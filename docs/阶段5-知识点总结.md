> 阶段 5 目标：让产品首次具备**非文本模态**能力——既能"看懂"用户上传的图片（图片理解），也能"画出来"用户描述的内容（文生图）。

## 1. 主线（计划内）：两种多模态任务的本质区别

多模态在工程上分成两大方向，API 形态完全不同，务必分清：

| 方向 | 输入 | 输出 | 典型场景 | Spring AI 抽象 |
|---|---|---|---|---|
| **图片理解（理解型）** | 图片 + 文字 | 文字 | 识图、OCR、图表解读 | `ChatClient` + `Media` |
| **文生图（生成型）** | 文字 | 图片 | 海报、插画、素材 | `ImageModel` + `ImagePrompt` |

- 图片理解本质是**多模态对话**：把图片作为一条"带附件的消息"发给 ChatModel，模型还是吐文字。
- 文生图本质是**独立生成任务**：走专门的 `ImageModel`（不是 ChatModel），调用方式、返回结构都不同。

本项目两类任务都用 DashScope，但分别由它自动配置的**两个不同的 Bean** 承担（`dashScopeChatModel` 管理解、`dashScopeImageModel` 管生成），互不干扰。

## 2. 核心原语（Spring AI 1.1.2 实测 API，文档不准须以 jar 为准）

### 2.1 图片理解：把图片封装成 `Media`，随 UserMessage 发出

```java
// 1) 把上传的字节包成 Resource（Spring AI 的 Media.data 接受 Resource / byte[] / URL 字符串）
byte[] bytes = image.getBytes();
String contentType = image.getContentType();
if (contentType == null || contentType.isBlank()) contentType = "image/png"; // 兜底，见 §4 坑3
Media media = Media.builder()
        .mimeType(MimeTypeUtils.parseMimeType(contentType))
        .data(new ByteArrayResource(bytes))
        .build();

// 2) Spring AI 1.1.2：user() 不吃 UserMessage，必须用 Consumer<PromptUserSpec> 在 spec 里 text + media
String answer = multimodalClient.prompt()
        .user(u -> u.text(question).media(media))
        .call()
        .content();
```

**关键理解**：在 OpenAI 兼容协议下，带图的消息最终会被序列化成
`content = [ {type:"text", text:question}, {type:"image_url", image_url:{url:"data:image/png;base64,..."}} ]`。
`Media` 就是"图片附件"的载体，Spring AI 负责把它编成上面的 `image_url` 块；模型收到后就能"看图"。

> ⚠️ **`qwen-vl-max` 必须开 `multi-model: true`**（见 §4 坑4）。这是 DashScope 视觉模型的开关：
> 开着 → 请求走**多模态端点**，图片被识别；关着 → 请求打到**文本端点**，图片被直接丢弃，模型回"看不到图"。

### 2.2 文生图：标准的 `ImageModel` 抽象

```java
// 注入 Spring AI 标准的 ImageModel（DashScope 自动配置的实现是 DashScopeImageModel）
@PostMapping("/generate")
public Map<String, Object> generate(@RequestBody Map<String, String> body) {
    String prompt = body.get("prompt");
    ImageResponse resp = imageModel.call(new ImagePrompt(prompt)); // 模型名/尺寸来自 yml 的 image.options
    String url = resp.getResult().getOutput().getUrl();           // 通义万相返回的是"临时图片 URL"
    String dataUrl = downloadAsDataUrl(url);                      // 后端代理下载 → base64 data URL（见 §4 坑6）
    return Map.of("image", dataUrl, "url", url);
}
```

`ImageModel` 是 Spring AI 对"文生图"的统一抽象（类似 `ChatModel` 对对话的抽象），背后可换不同厂商（DashScope / OpenAI / Stability...）。本项目的实现类由 dashscope starter 提供，模型名 / 分辨率在 `application.yml` 的 `spring.ai.dashscope.image.options` 配置，**代码里不必硬编码**。

## 3. 两个端点讲清楚

### 3.1 `POST /api/multimodal/describe`（图片理解）
- 消费 `multipart/form-data`，字段：`image`（文件）+ `question`（文字，可空，默认"请描述这张图片的内容"）。
- 把图转成 `Media` → 交给 `multimodalClient`（底层 `dashScopeChatModel` / `qwen-vl-max`）→ 返回 `{ "answer": "..." }`。
- 不挂记忆 Advisor（一次性视觉问答，不该写进多轮对话记忆，与阶段 2 的 `parsingClient` 同理）。

### 3.2 `POST /api/multimodal/generate`（文生图）
- 消费 `application/json`，字段：`prompt`。
- 调 `imageModel.call(new ImagePrompt(prompt))` → 拿到图片 URL → **后端代理下载成 base64 data URL** 返回 `{ "image": "data:image/png;base64,...", "url": "..." }`。
- 前端 `<img src="data:...">` 直接显示，不受 DashScope 临时 URL 过期影响。

### 3.3 配置（application.yml 关键段）
```yaml
spring:
  ai:
    dashscope:
      api-key: ${AI_DASHSCOPE_API_KEY:}      # 复用阿里云 DashScope Key
      retry:                                  # 文生图是异步任务，放大轮询次数避免"still pending"误判失败
        max-attempts: 20
        backoff: { initial-interval: 3s, multiplier: 2, max-interval: 15s }
      chat:
        options:
          model: qwen-vl-max                  # 视觉模型
          multi-model: true                   # ⚠️ 必须开：走多模态端点，否则图片被丢
      image:
        options:
          model: wanx2.0-t2i-turbo            # 通义万相（更快/更便宜的 turbo 版）
          size: 1024*1024
```

### 3.4 依赖（pom.xml）
```xml
<dependency>
    <groupId>com.alibaba.cloud.ai</groupId>
    <artifactId>spring-ai-alibaba-starter-dashscope</artifactId>
    <!-- 版本由 spring-ai-alibaba 的 BOM 统一管理，无需写 version -->
</dependency>
```
> 这个 starter 一次性自动配置**两个** Bean：`dashScopeChatModel`（ChatModel，归图片理解用）与 `dashScopeImageModel`（ImageModel，归文生图用）。它们与 DeepSeek / Ollama 的 ChatModel 通过 `@Qualifier` 区分，完全不冲突。

## 4. 踩坑大全（阶段 5 真实踩过的 6 个坑）

| # | 坑 | 现象 | 解决 |
|---|---|---|---|
| 1 | **DeepSeek V4 公开 API 是 text-only** | 模型返回"无法看到您提到的图片"，文字却能正常收到 | 图片理解改走 `qwen-vl-max`（DashScope）;`deepseek-v4-flash` 仅保留用于纯文本对话 |
| 2 | Spring AI 1.1.2 `UserMessage(String, List<Media>)` 构造器不存在 + `user()` 不吃 `UserMessage` | 编译报错 | 改用 `user(Consumer<PromptUserSpec>)`：`u -> u.text(question).media(media)` |
| 3 | 浏览器 `getContentType()` 可能为 null | `MimeTypeUtils.parseMimeType(null)` 抛异常 | 为 null 时兜底 `image/png` |
| 4 | `qwen-vl-max` 没开 `multi-model` | 请求打到文本端点，图片被丢弃，依然"看不到图" | yml 配 `spring.ai.dashscope.chat.options.multi-model: true` |
| 5 | 通义万相是**异步生成** | 默认重试次数不够 → "still pending" 误判失败 | yml 放大 `retry.max-attempts=20` + 指数退避 |
| 6 | 万相返回的图片 URL 是**临时 URL** | 前端直接 `<img src=url>` 过一会儿 403 加载失败 | 后端 `HttpClient` 代理下载成 base64 data URL 再返回 |

> 坑 1 是**方向性错误**（一开始误信"deepseek-v4-flash 原生支持图片输入"）。事实：截至 2026-08，DeepSeek V4 公开 API（`api.deepseek.com`）把图片当纯文本忽略。教训：**多模态视觉一定要用明确支持图片输入的模型**（qwen-vl-max / qwen-vl-plus / GPT-4o 等），不要赌纯文本模型"刚好"支持。

## 5. 端到端数据流

### 5.1 图片理解
```
浏览器选图 → FormData(image + question) → POST /api/multimodal/describe
  → Controller 读 bytes → Media(mimeType + ByteArrayResource)
  → multimodalClient.prompt().user(u -> u.text(question).media(media))
  → dashScopeChatModel(qwen-vl-max, multi-model=true) 把图编成 image_url 块发往多模态端点
  → 模型返回文本 → { answer }
  → 前端渲染到结果区
```

### 5.2 文生图
```
浏览器填 prompt → JSON { prompt } → POST /api/multimodal/generate
  → imageModel.call(ImagePrompt(prompt))  （DashScopeImageModel / 通义万相，异步轮询直至出图）
  → 拿到临时图片 URL → 后端 HttpClient 下载字节 → 编码 base64 data URL
  → { image: "data:image/png;base64,..." } → 前端 <img> 显示
```

## 7. 前后阶段衔接

- **依赖阶段 3 预留**：阶段 3 时就在 pom 注释里留了 `dashscope` 的口子（"DeepSeek 不提供 embedding / 图片能力，到时再加 dashscope"）。阶段 5 只是把它落实，无破坏性改动。
- **与已有模型栈共存**：现在模型阵容 = DeepSeek V4（对话）+ qwen-vl-max（视觉理解）+ Wanx（文生图）+ Ollama bge-m3（embedding）。四类职责清晰，靠 `@Qualifier` 区分，互不打扰。
- **为阶段 6/7 铺路**：多模态让 Agent 第一次能"看见"世界——后续 Agent 编排 / MCP 接入外部工具时，可以让"看图说话""生成配图"成为 Agent 可调用的能力（类比阶段 4 把 RAG 变成 `RagQueryTool`）。
- **工程化提醒**：文生图涉及"图片落盘 / 存储 / 鉴权"，后续阶段 8 做工程化时要考虑生成内容的合规与安全（Guardrails）。
