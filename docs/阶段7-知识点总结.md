# 阶段 7 知识点总结 —— MCP 集成（Model Context Protocol）让 Agent 调用远程工具

> 阶段 7 目标：把"工具"从**进程内 `@Tool` 方法**升级成**跨进程、跨语言的标准协议**。Agent 不再只能调用同进程的 Java 方法，还能调用一个独立的 Python 进程、一个独立的 Java 微服务——只要它们实现了 MCP 协议。这是从"单体 Agent"走向"工具即服务"的关键一步。
> 你已本地调试 + 验证全部通过 ✅（stdio 4 工具 + SSE 4 工具 = 8 个 MCP 工具，`/mcp/tools` 返回 8），本篇把协议概念、双路架构、依赖选型大坑、配置分层坑、验证清单一并固化。

---

## 0. 一句话心智模型

> **MCP（Model Context Protocol）= 给"AI 调用工具"定了一个标准协议。** 以前 Agent 调工具，工具必须和 Agent 跑在同一个进程里（阶段 4 的 `@Tool`）；有了 MCP，工具可以是一个独立进程、独立服务、甚至独立语言写的——Agent（MCP Client）和工具（MCP Server）用 JSON-RPC over stdio/SSE 通信，互不耦合。
>
> 再补一句定位：MCP 由 Anthropic 提出，Spring AI 1.1.2 内置了 Client + Server 双向支持。**它本质上是"工具的 HTTP"**——就像 HTTP 让浏览器能访问世界上任何 Web 服务器，MCP 让 Agent 能调用世界上任何 MCP Server 暴露的工具。

阶段 7 能力拼图（每个 = 一块可独立讲解的能力）：

| 能力 | 一句话 |
|---|---|
| MCP 概念 | JSON-RPC 协议，Client 发 `tools/list` 发现工具、发 `tools/call` 调用工具；传输层 stdio / SSE / Streamable HTTP 三选一 |
| stdio 路线（Python Server） | 主应用启动一个 Python 子进程，通过标准输入/输出收发 JSON-RPC，发现 4 个 Python 工具 |
| SSE 路线（Java Server） | 独立 Java 微服务通过 SSE 端点暴露 4 个工具，主应用作为 SSE Client 连接调用 |
| Nacos 注册 | Java MCP Server 把工具元数据注册到 Nacos，本来想让主应用"服务发现"——但 1.1.x 客户端发现另有设计（见第 5 章） |
| 多模块工程 | 根 POM `packaging=pom`，下挂 `ai-workshop`（主应用 9999）+ `mcp-nacos-server`（MCP Server 9988） |
| 工具汇聚 | `McpConfig` 收集所有 MCP `ToolCallback` → `Agent6Config` 注入 `mcpChatClient` → Agent 无感调用远程工具 |
| 依赖选型（最大坑） | `mcp-registry` / `nacos-mcp-client` / `mcp-router` 三个 artifact 职责完全不同，选错则 `/mcp/tools` 返回空 |

## 1. 主线：MCP 是什么 + 双路集成架构

### 1.1 MCP 解决什么问题

阶段 4 的工具调用是**进程内**的：

```
Agent（Java 进程）──直接调用──→ @Tool 方法（同一个 Java 进程里的 Bean）
```

问题：工具必须用 Java 写、必须和 Agent 同进程、Agent 重启工具也跟着重启、工具想换个实现得改 Agent 代码。

MCP 把"工具"拆成独立的服务端：

```
Agent（MCP Client）──JSON-RPC──→ MCP Server（独立进程/服务，任意语言）
                                  ├── 暴露 tools/list：我有哪些工具
                                  └── 暴露 tools/call：执行某个工具
```

这样工具可以**独立部署、独立扩缩容、跨语言**。Python 写的工具、Java 写的工具、甚至第三方提供的 MCP Server，Agent 都能调。

> 类比：阶段 4 的 `@Tool` 像"内置函数"；MCP 工具像"远程 API"。前者快但耦合，后者多一跳网络但解耦。

### 1.2 双路集成架构（最终落地形态）

本项目用 MCP 的两种传输方式各跑一路，互为对照：

## 2. stdio 路线：Python MCP Server

### 2.1 Python 端：FastMCP

`mcp-servers/python-server/server.py` 用 `fastmcp` 库（mcp 包的高层 API）。核心三步：

```python
from fastmcp import FastMCP

# 第一步：创建 MCP 服务实例（name 会显示在 Spring AI 连接配置里）
mcp = FastMCP("python-tools-server")

# 第二步：用 @mcp.tool() 装饰器注册工具
# 函数名 = 工具名，docstring = 工具描述，参数类型注解 = 入参 schema
# 关键：参数类型只能用基础类型（str/int/float/bool），不能是复杂对象
@mcp.tool()
def get_current_time() -> str:
    """获取当前日期和时间，返回 YYYY-MM-DD HH:MM:SS 格式的字符串。"""
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

# 第三步：启动服务（stdio 传输）
if __name__ == "__main__":
    mcp.run(transport="stdio")
```

> Python 基础提示（给不熟 Python 的你）：
> - `if __name__ == "__main__":` 是 Python 的"入口保护"——脚本被直接运行时才执行 `mcp.run()`；被 import 时不执行。等价于 Java 的 `public static void main`。
> - `transport="stdio"` 表示用**标准输入/输出**通信：Spring Boot 往 Python 进程的 stdin 写 JSON-RPC 请求，Python 从 stdout 读出响应。不占用任何网络端口。
> - `@mcp.tool()` 是装饰器（decorator），类似 Java 的注解，把普通函数注册成 MCP 工具。

4 个工具：`get_current_time`（时间）、`get_weather`（模拟天气）、`calculate`（AST 安全求值，**不用 `eval()`** 防注入）、`search_knowledge`（模拟知识库检索）。

`requirements.txt`：

```
mcp>=2.0.0
fastmcp==3.4.7
```

> 小提醒：`fastmcp` 那行必须是双等号 `==`（pip 的版本指定语法），单等号 `=` 会被 pip 拒绝。本地若已用 `pip install fastmcp==3.4.7` 装好则不影响运行，但文件里建议改对。

### 2.2 主应用端：配置 + 启动原理

主应用 `application.yml`：

```yaml
spring:
  ai:
    mcp:
      client:
        enabled: true
        name: ai-workshop-mcp-client
        version: 1.0.0
        type: async                   # 异步模式（支持 SSE/stdio 并发）
        toolcallback:
          enabled: true               # 启用后自动产生 ToolCallbackProvider bean
        # ---- stdio 连接：Python MCP Server ----
        stdio:                        # ⚠️ 注意前缀是 .stdio，每种传输各一层（见第 6 章）
          connections:
            python-tools-server:      # 连接名（任意，唯一即可）
              command: ${MCP_PYTHON_PATH:python}
              args:
                - ${MCP_PYTHON_SERVER:/Users/.../mcp-servers/python-server/server.py}
```

启动时 Spring AI MCP Client 自动配置会：
1. 读到 `stdio.connections.python-tools-server` → 用 `command` + `args` 拉起一个 Python 子进程
2. 通过 stdin 发 MCP `initialize` 握手 → 发 `tools/list` 拿到 4 个工具定义
3. 为每个工具创建一个 `ToolCallback` 实例，汇总成名为 **`mcpAsyncToolCallbacks`** 的 `ToolCallbackProvider` bean（`type: async` 时叫这个名字；`sync` 时叫 `mcpSyncToolCallbacks`）

> 关键：这个 bean 名 `mcpAsyncToolCallbacks` 是 Spring AI 自动配置**写死**的，注入时要 `@Qualifier("mcpAsyncToolCallbacks")` 精确指定（见 4.1）。

### 2.3 通信流程

```
主应用                          Python 子进程
  │                                │
  │── spawn: python server.py ────→│ （进程启动，mcp.run() 阻塞读 stdin）
  │                                │
  │── stdin: initialize ──────────→│
  │←─ stdout: initialize result ───│
  │                                │
  │── stdin: tools/list ──────────→│ （发现工具）
  │←─ stdout: [4 个工具定义] ───────│
  │                                │
  │  （之后 Agent 调用时）           │
  │── stdin: tools/call(get_weather, {city:"北京"}) ─→│
  │←─ stdout: "北京天气：晴，25°C..." ─────────────────│
```

子进程的生命周期跟主应用绑定——主应用停，子进程也被关。

## 3. SSE 路线：Java MCP Server + Nacos 注册

### 3.1 服务端：mcp-nacos-server

独立 Spring Boot 应用，端口 9988。两个核心类：

**`McpToolsConfig`——用 `@Tool` 定义工具（和阶段 4 完全一样的写法）：**

```java
@Service  // 注册为 Spring Bean，使 @Tool 方法能被 MCP Server 扫描到
public class McpToolsConfig {

    @Tool(description = "生成 UUID v4 唯一标识符。count 指定生成数量（1-10），默认 1 个。")
    public String generateUuid(@ToolParam(description = "生成数量，默认 1，最多 10") int count) {
        // ... 生成 UUID
    }

    @Tool(description = "在指定范围内生成一个随机整数（包含最小值和最大值）。")
    public String randomNumber(@ToolParam(description = "最小值（含）") int min,
                                @ToolParam(description = "最大值（含）") int max) {
        // ...
    }

    // textStats / serverStatus 同理
}
```

**`McpProviderConfig`——把工具打包成 `ToolCallbackProvider`：**

```java
@Configuration
public class McpProviderConfig {
    @Bean
    public ToolCallbackProvider weatherTools(McpToolsConfig mcpTools) {
        // MethodToolCallbackProvider 扫描 mcpTools 上的 @Tool 方法，生成 ToolCallback 列表
        return MethodToolCallbackProvider.builder().toolObjects(mcpTools).build();
    }
}
```

> 这个 `ToolCallbackProvider` bean 是关键——`spring-ai-starter-mcp-server-webflux` 启动时会找容器里所有 `ToolCallbackProvider`，把它们的工具通过 SSE 端点暴露出去。没有这个 bean，MCP Server 不会暴露任何工具。

服务端配置 `application.yml`：

```yaml
server:
  port: 9988
spring:
  application:
    name: mcp-nacos-server
  ai:
    mcp:
      server:
        type: async          # 异步模式（SSE 传输）
        name: mcp-nacos-server
        version: 1.0.0
        instructions: generate_uuid：... - random_number：... - text_stats：... - server_status：...
```

启动后暴露两个端点（Spring AI 1.1.2 默认值，反编译 `McpServerSseProperties` 坐实）：
- `GET /sse`——SSE 长连接端点（客户端连这个）
- `POST /mcp/message`——工具调用消息端点（注意 1.1.2 默认是 `/mcp/message`，老版本是 `/message`）

### 3.2 Nacos 注册（mcp-registry）

服务端再引入 `spring-ai-alibaba-starter-mcp-registry`（1.1.2.1），配置 Nacos 连接：

```yaml
spring:
  ai:
    alibaba:
      mcp:
        nacos:
          server-addr: localhost:8848    # Nacos API 端口（3.x 控制台在 8080）
          namespace: public
          username: nacos                # Nacos 3.x 强制鉴权
          password: ${NACOS_PASSWORD:123456}
          register:
            enabled: true                # 启动时自动注册 MCP 元数据到 Nacos
```

启动后，mcp-registry 的 `NacosMcpRegisterAutoConfiguration` 会把 MCP Server 的元数据（名称、版本、工具列表、SSE 端点地址）写进 Nacos。在 Nacos 控制台（`http://localhost:8080`）能看到注册的 MCP 服务。

> ⚠️ 注意：mcp-registry **只做"服务端 → Nacos"的单向注册**，不做"客户端 ← Nacos"的发现。这是第 5 章大坑的根源。

### 3.3 主应用端：SSE 直连（方案 B 最终落地）

主应用 `application.yml` 的 SSE 配置：

```yaml
spring:
  ai:
    mcp:
      client:
        # ...（通用配置见 2.2）
        sse:                              # ⚠️ 前缀是 .sse，不是 .connections（见第 6 章）
          connections:
            nacos-mcp-server:             # 连接名（任意，唯一即可）
              url: ${MCP_NACOS_URL:http://localhost:9988}
              sse-endpoint: ${MCP_NACOS_SSE_ENDPOINT:/sse}
```

启动时 Spring AI MCP Client：
1. 读到 `sse.connections.nacos-mcp-server` → 创建一个 SSE Client Transport，连 `http://localhost:9988/sse`
2. 握手 + `tools/list` → 发现 4 个 Java 工具
3. 同样汇入 `mcpAsyncToolCallbacks` 这个 `ToolCallbackProvider`（和 stdio 的工具合在一起）

> 配置用了 `${MCP_NACOS_URL:...}` 环境变量占位——换端口/换机器只改环境变量，不动代码。这是阶段 7 的工程化小细节。

## 4. 工具汇聚与 Agent 接入

### 4.1 McpConfig：收集所有 MCP ToolCallback

```java
@Configuration
public class McpConfig {

    // ⚠️ @Qualifier 精确指定 bean 名：
    //   type=async  → Spring AI 自动配置产生的 bean 叫 mcpAsyncToolCallbacks
    //   type=sync   → 叫 mcpSyncToolCallbacks
    // 不写 @Qualifier 的话，Spring 按类型注入 ToolCallbackProvider 也行，
    // 但容器里若有多个同名类型 bean 会歧义，显式 Qualifier 最稳。
    @Qualifier("mcpAsyncToolCallbacks")
    @Autowired
    ToolCallbackProvider mcpToolCallbackProvider;

    /**
     * 汇聚所有 MCP 来源的 ToolCallback（Python stdio + Nacos SSE）。
     * 如果 MCP 未启用或连接失败，Spring 注入空列表，不会导致启动失败——
     * MCP 是可选增强能力，不影响核心功能。
     */
    @Bean
    public List<ToolCallback> mcpToolCallbacks() {
        if (mcpToolCallbackProvider != null && mcpToolCallbackProvider.getToolCallbacks() != null) {
            return Arrays.asList(mcpToolCallbackProvider.getToolCallbacks());
        }
        return new ArrayList<>();
    }
}
```

> 为什么不直接注入 `ToolCallbackProvider` 给 Agent，而要包一层 `List<ToolCallback>`？
> - 统一类型：后续 `Agent6Config` 同时注入本地 `@Tool` 对象和远程 MCP 工具，用 `List<ToolCallback>` 统一管理更清晰。
> - 空安全：MCP 连接失败时返回空列表，调用方不用判空。

### 4.2 Agent6Config：@Lazy 注入 + mcpChatClient

```java
public Agent6Config(@Qualifier("deepSeekChatModel") ChatModel deepSeek,
                    DateTimeTool dateTimeTool, /* ... 阶段4的5个本地工具 ... */
                    @Lazy List<ToolCallback> mcpToolCallbacks) {  // ⚠️ @Lazy
    // ...
    this.mcpTools = mcpToolCallbacks != null ? mcpToolCallbacks : List.of();
}

@Bean
public ChatClient mcpChatClient(@Qualifier("deepSeekChatModel") ChatModel deepSeek) {
    var builder = ChatClient.builder(deepSeek);
    if (!mcpTools.isEmpty()) {
        // ⚠️ defaultToolCallbacks(ToolCallback...) 而非 defaultTools(Object...)
        // 因为 MCP 工具以 ToolCallback 接口实例注入，不走 @Tool 注解扫描
        builder.defaultToolCallbacks(mcpTools);
    }
    return builder.build();
}
```

两个关键点：

1. **`@Lazy` 注入**：MCP 工具 bean 的初始化依赖子进程启动 / 远程连接握手，可能比 `Agent6Config` 慢。加 `@Lazy` 让 Spring 在真正使用时才解析这个依赖，避免启动时的循环依赖或时序问题。

2. **`defaultToolCallbacks` vs `defaultTools`**：
   - `defaultTools(Object...)`——给 `@Tool` 注解的 Bean 用，框架会反射扫描注解
   - `defaultToolCallbacks(ToolCallback...)`——给已经是 `ToolCallback` 实例的用（MCP 工具就是这种），直接注册不再扫描
   - 选错重载，工具不会被识别。

### 4.3 Agent6Controller：/mcp/tools + /mcp/chat

```java
@GetMapping("/mcp/tools")
public Map<String, Object> mcpTools() {
    Map<String, Object> res = new LinkedHashMap<>();
    res.put("total", mcpToolCallbacks.size());
    res.put("tools", mcpToolCallbacks.stream().map(tc -> {
        Map<String, Object> info = new LinkedHashMap<>();
        info.put("name", tc.getToolDefinition().name());
        info.put("description", tc.getToolDefinition().description());
        return info;
    }).collect(Collectors.toList()));
    return res;
}

@PostMapping("/mcp/chat")
public Map<String, Object> mcpChat(@RequestBody Map<String, String> body) {
    String query = body.getOrDefault("query", "");
    // mcpChatClient 已挂载所有 MCP 工具，模型会自主决定调哪个
    String result = mcpChatClient.prompt().user(query).call().content();
    // ...
}
```

验证通过时 `GET /mcp/tools` 返回 8 个工具（stdio 4 + sse 4），`POST /mcp/chat` 带自然语言提问，模型自主调用远程工具并返回结果。

## 5. 依赖选型专题（最大坑）

这是阶段 7 耗时最多的排查。核心问题：**主应用 `/mcp/tools` 一度只返回 4 个（stdio），Nacos 那 4 个缺失**。根因不是配置，是依赖选错。

### 5.1 三个 artifact 的真实职责（反编译结论）

本地仓库里同时存在三个名字相似的 SAA MCP artifact，职责完全不同：

| artifact | 版本 | 真实职责（反编译 AutoConfiguration.imports 坐实） | 用在哪 |
|---|---|---|---|
| `spring-ai-alibaba-starter-mcp-registry` | 1.1.2.1 | **服务端注册**：`NacosMcpRegisterAutoConfiguration` / `NacosStatelessMcpRegisterAutoConfiguration` / `McpTracingAutoConfiguration`。注册类方法参数含 `McpSyncServer`/`McpAsyncServer` bean | **MCP Server 端**（mcp-nacos-server） |
| `spring-ai-alibaba-starter-nacos-mcp-client` | 1.0.0.2 | **客户端发现（1.0.x 设计）**：`NacosMcpSseClientAutoConfiguration`（从 Nacos 查端点→校验 mcp-sse→建 transport）/ `NacosMcpToolCallbackAutoConfiguration`（产出 ToolCallback） | 客户端（已弃用方向） |
| `spring-ai-alibaba-mcp-router` | 1.1.2.1 | **客户端发现（1.1.x 设计）**：`NacosMcpRouterAutoConfiguration` / `FileMcpRouterAutoConfiguration` / `DbMcpRouterAutoConfiguration`。核心类 `McpServiceDiscovery` / `McpRouterWatcher` / `McpServerVectorStore` | 客户端（1.1.x 推荐方向） |

### 5.2 为什么 /mcp/tools 一度返回空（Nacos 部分）

排查时的错误依赖组合：主应用引入了 `mcp-registry`（想用它做客户端发现）。但：

1. mcp-registry 的自动配置全是**服务端注册**类，方法参数需要 `McpSyncServer`/`McpAsyncServer` bean
2. 主应用是纯客户端，**没有这些 bean** → 自动配置条件不满足 → **全部静默跳过**
3. 不产生任何 Nacos 工具 → `/mcp/tools` 只剩 stdio 的 4 个

一句话：**mcp-registry 是给 Server 用的（注册自己到 Nacos），不是给 Client 用的（从 Nacos 发现别人）。** 名字有迷惑性，但职责单向。

### 5.3 三种客户端发现方案对比

想让主应用"通过 Nacos 动态发现 MCP Server"，1.1.x 生态里有三条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 旧客户端直连 Nacos | 主应用引入 `nacos-mcp-client:1.0.0.2`（显式版本，不在 1.1.2 BOM 里） | 保留 Nacos 动态发现，配置不改 | 1.0.x 旧 artifact，与 1.1.2 生态混搭；其 `mcp-nacos` 与 1.1.2.1 的 `mcp-common` 有同名类冲突风险 |
| B. 标准 SSE 直连（**本项目选**） | 主应用用 Spring AI 原生 `spring.ai.mcp.client.sse.connections` 直连 `localhost:9988` | 全 1.1.2 原生、最简单、最稳 | 地址写死，无服务发现，学不到 Nacos 那条线 |
| C. mcp-router 中间层 | 部署一个 mcp-router 服务，主应用连 router，router 从 Nacos/File/DB 聚合多 MCP Server | 工具聚合 / 动态增减 / 语义检索（`McpServerVectorStore`）/ 统一治理 | 多部署一个服务，架构更重 |

### 5.4 mcp-router 那层是干嘛的（设计取舍）

反编译 `spring-ai-alibaba-mcp-router-1.1.2.1` 看到的核心类：

```
McpServiceDiscovery           ← 服务发现抽象接口
├── NacosMcpServiceDiscovery  ← 从 Nacos 发现 MCP Server
├── FileConfigMcpServiceDiscovery  ← 从配置文件发现
├── DbMcpServiceDiscovery     ← 从数据库发现
└── CompositeMcpServiceDiscovery   ← 复合多源

McpRouterWatcher / AbstractRouterWatcher   ← 监听 MCP Server 上下线，动态更新
McpServerVectorStore / SimpleMcpServerVectorStore  ← 把 MCP Server 当向量，支持语义检索
```

所以 1.1.x 的设计哲学是：**Client 不直连 Nacos 发现 MCP Server，而是连一个 mcp-router 中间层**，router 负责从 Nacos/File/DB 聚合多个 MCP Server 再统一暴露给 Client。这是"加了一层"——换来的是：

- **工具聚合**：Client 只连 router 一处，就能用到 router 背后所有 MCP Server 的工具
- **动态增减**：MCP Server 上下线，router 监听 Nacos 自动更新，Client 无感
- **语义检索**：`McpServerVectorStore` 暗示能按语义找最相关的 MCP Server/工具
- **统一治理**：鉴权、限流、可观测都在 router 层做一次

对比 1.0.x 的 `nacos-mcp-client`（Client 直连 Nacos 发现），1.1.x 用 router 中间层是架构升级，不是 bug。**本项目为学习 MCP 协议本身，选了最简单的方案 B（直连），把 Nacos 服务发现 + mcp-router 留作后续进阶。**

### 5.5 最终落地的依赖

- **mcp-nacos-server（服务端）pom**：`spring-ai-starter-mcp-server-webflux` + `spring-ai-alibaba-starter-mcp-registry` ✅（registry 在服务端方向正确）
- **ai-workshop（客户端）pom**：`spring-ai-starter-mcp-client-webflux` ✅（已删除错误的 mcp-registry）

## 6. 配置坑：transport 分层

### 6.1 正确的属性前缀（反编译坐实）

Spring AI 1.1.2 的 MCP Client 配置**按传输类型分层**，每种传输各占一个属性节点。反编译三个属性类的 `@ConfigurationProperties` 前缀：

| 属性类 | 绑定前缀 | 含义 |
|---|---|---|
| `McpClientCommonProperties` | `spring.ai.mcp.client` | 通用：`enabled` / `name` / `version` / `type` / `toolcallback` |
| `McpStdioClientProperties` | `spring.ai.mcp.client.stdio` | stdio 连接：`connections.<name>.{command,args,env}` |
| `McpSseClientProperties` | `spring.ai.mcp.client.sse` | SSE 连接：`connections.<name>.{url,sseEndpoint}` |
| `McpStreamableHttpClientProperties` | `spring.ai.mcp.client.streamable-http` | Streamable HTTP 连接 |

正确的配置结构：

```yaml
spring:
  ai:
    mcp:
      client:              # 通用层
        enabled: true
        type: async
        stdio:             # stdio 连接在这一层
          connections:
            python-tools-server: { command: ..., args: [...] }
        sse:               # sse 连接在这一层（不是在 connections 下用 type 区分！）
          connections:
            nacos-mcp-server: { url: ..., sse-endpoint: /sse }
```

### 6.2 错误写法对照（排查中踩过的坑）

❌ **错误**：把所有连接塞进同一个 `connections`，用 `type` 区分传输类型：

```yaml
spring:
  ai:
    mcp:
      client:
        connections:          # ← 错！没有这个前缀
          nacos-server:
            type: sse          # ← 错！type 是 client 级属性（async/sync），不是 per-connection
            url: http://localhost:9988
            sseEndpoint: /sse
```

这种写法 Spring AI 完全不识别（没有 `spring.ai.mcp.client.connections` 这个属性绑定），连接不会被创建，`/mcp/tools` 自然为空。

✅ **正确**：每种传输各有独立节点，`SseParameters` 只有 `url` + `sseEndpoint` 两个字段（无 `type`）：

```yaml
spring:
  ai:
    mcp:
      client:
        sse:                  # ← SSE 连接在 .sse 节点下
          connections:
            nacos-mcp-server:
              url: http://localhost:9988
              sse-endpoint: /sse   # kebab-case，Spring Boot relaxed binding 兼容 sseEndpoint
```

> 记忆口诀：**stdio/sse/streamable-http 是"并列的三兄弟"，各自占 `spring.ai.mcp.client.<transport>.connections` 一个节点；不是"一个 connections 里用 type 分"。** 看已有的 stdio 配置长什么样，sse 照着改前缀就行。

## 7. Nacos 3.x 关键变化（docker/nacos-standalone.yml）

本项目用 Nacos 3.2.3，相对 2.x 有几个破坏性变化：

| 变化点 | 2.x | 3.x |
|---|---|---|
| 控制台端口 | 8848 | **8080**（API 端口 8848 不变） |

| API 路径 | /v1 /v2 | 新增 /nacos/v3/（向下兼容 /v1 /v2） |

docker compose 关键配置：

```yaml
services:
  nacos:
    image: nacos/nacos-server:v3.2.3
    environment:
      - MODE=standalone
      - NACOS_AUTH_TOKEN=VtWI3RWawiflt0tdccZHH83wFJJ16oOdUwZGWr07XsvBaFS6Zern5T0lgjHSCm/E  # JWT 签名密钥（Base64，>32 字符）

      - NACOS_AUTH_IDENTITY_VALUE=nacos_dev_identity_value

      - "8080:8080"   # 控制台
```

|---|---|

| `POST http://localhost:9999/mcp/chat` body `{"query":"现在几点"}` | 模型调用 `get_current_time`（Python stdio 工具）返回时间 |
| `POST http://localhost:9999/mcp/chat` body `{"query":"生成 3 个 UUID"}` | 模型调用 `generateUuid`（Java SSE 工具）返回 UUID |
| Nacos 控制台 | 服务列表能看到 `mcp-nacos-server` 注册项 |

排查命令（启动类里加的 `CommandLineRunner`）：

```java
@Bean
public CommandLineRunner checkMcpBeans(ApplicationContext context) {
    return args -> {
        // 打印容器里所有 ToolCallbackProvider bean，确认 stdio + sse 两路都注入
        Map<String, ToolCallbackProvider> beans =
            context.getBeansOfType(ToolCallbackProvider.class);
        beans.forEach((name, provider) -> {
            System.out.println("[" + name + "] tools=" +
                Arrays.toString(provider.getToolCallbacks()));
        });
    };
}
```

> 这个 runner 在排查时很有用：能看到容器里实际有几个 `ToolCallbackProvider`、各带几个工具。如果只看到 stdio 那个、没有 sse，说明 SSE 连接没建起来（配置前缀错 / 服务端没起 / 端点不对）。

## 11. 阶段 7 的定位（承上启下）

- **承接阶段 4/6**：阶段 4 让 Agent 能调进程内 `@Tool`；阶段 6 让多个 Agent 协作；阶段 7 把"工具"从进程内解放成跨进程标准协议——Agent 能调的工具池从"5 个本地方法"扩展到"任意 MCP Server"。
- **指向阶段 8**：MCP 让工具可以远程化、服务化，为阶段 8 工程化（可观测、Guardrails、Docker 化部署）打下基础——远程 MCP Server 本身就是微服务，天然需要可观测和治理。
- **未走的路**：mcp-router 中间层（工具聚合 + 语义检索 + 动态发现）是 1.1.x 的进阶方向，本项目为聚焦 MCP 协议本身暂未引入，留作后续。

> 一句话收尾：**MCP 让"工具"变成"服务"。** 阶段 4 你学会了让 Agent 调函数，阶段 7 你学会了让 Agent 调远程服务——往后 Agent 的能力边界不再受限于你的进程，而受限于你能部署多少 MCP Server。
