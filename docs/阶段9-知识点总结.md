# 阶段 9 知识点总结 —— 用户体系与演示加固：登录 + 隔离 + 限流

> 学习主线：把"单机自嗨的工具"变成"敢给别人体验的演示系统"——**先管住身份**（登录），**再管住数据**（用户隔离），**最后管住滥用**（限流 + 注册开关）。

---

## 0. 一句话心智模型

**演示系统 = 身份认证（你是谁）+ 数据隔离（只能看自己的）+ 资源限制（防恶意刷）** 三层，对应三大件：

- **Spring Security + JWT**：无状态认证，谁都能登录（或只有 admin）；
- **user_id 全链路隔离**：所有业务表挂归属用户，查询/写入/越权校验在 Service 层收口；
- **限流 + 注册开关**：按"用户 + IP"双维度按天配额，超限 429；注册接口默认关闭、Service 层强校验防直调。

## 1. 需求与方案选型

### 1.1 需求（用户拍板 3 点）

| 需求 | 决策 |
|---|---|
| 可登录，逻辑与用户关联（对话历史/文档资料等用户级隔离） | Spring Security + JWT（无状态、前后端分离最合适） |
| 老数据归属 | 现有数据统一归 **admin**（一次性 UPDATE） |
| obs.html 可观测页 | 用户只看到**自己**的调用记录 |

### 1.2 为什么 JWT 而不是 Session

- **无状态**：演示系统多人并发、前后端分离，token 存 localStorage，服务器不存会话——水平扩展零成本；
- **教学价值**：JWT 的签名/过期/角色 claim 是标准知识，学会后所有前后端分离项目通用；
- 密码 **BCrypt**（Spring Security 内置）：加盐哈希，同样的密码每次加密结果不同，防彩虹表。

### 1.3 技术选型

| 组件 | 选择 |
|---|---|
| 认证框架 | `spring-boot-starter-security` |
| JWT 库 | `jjwt-api / jjwt-impl / jjwt-jackson` 0.12.x |
| 密码 | BCryptPasswordEncoder |
| 限流 | 自写拦截器 + `rate_limit_count` 表（无第三方依赖） |

## 2. 数据库层：users 表 + user_id 迁移

### 2.1 新增 users 表

```sql
CREATE TABLE IF NOT EXISTS users (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    username     VARCHAR(64)  NOT NULL,
    password     VARCHAR(100) NOT NULL,   -- BCrypt 哈希（60 字符）
    display_name VARCHAR(64)  DEFAULT NULL,
    role         VARCHAR(16)  NOT NULL DEFAULT 'USER',   -- ADMIN / USER
    enabled      TINYINT(1)   NOT NULL DEFAULT 1,
    created_at   TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2.2 6 张业务表加 user_id

`conversation` / `chat_log` / `chat_memory` / `rag_file` / `task_ticket` / `ai_call_log` 全部加 `user_id BIGINT DEFAULT NULL` + 索引。

### 2.3 恢复精简版 SchemaMigration（幂等迁移）

阶段 8 刚删过 SchemaMigration（当时 schema.sql 已全覆盖），阶段 9 又要加列——**结论：加列这种"存量库升级"还是需要启动时幂等迁移**，恢复一个精简版：

```java
// 启动时按顺序执行（每条幂等）：
// 1. CREATE TABLE IF NOT EXISTS users / rate_limit_count
// 2. 逐表检查列：SHOW COLUMNS LIKE 'user_id' → 没有就 ALTER TABLE ADD COLUMN
// 3. UPDATE conversation SET user_id = <adminId> WHERE user_id IS NULL  -- 老数据归 admin
// 4. 无 admin 时创建（BCrypt 加密，用户名/密码走环境变量）
```

**为什么用 ALTER 而不是重建表**：老库数据要保留（对话历史、上传文件），重建表会丢数据。`SHOW COLUMNS` 判断列存在性 → `ALTER TABLE ADD COLUMN` 是标准的"幂等加列"模式。

## 3. 认证骨架：SecurityConfig + JwtService + JwtAuthFilter

### 3.1 SecurityConfig（核心放行策略）

```java
.authorizeHttpRequests(auth -> auth
        // 放行：认证接口 + 静态资源（通配符！）+ 健康检查
        .requestMatchers("/api/auth/login", "/api/auth/register").permitAll()
        .requestMatchers("/", "/*.html", "/*.js", "/*.css", "/*.ico",
                "/*.png", "/*.jpg", "/*.jpeg", "/*.svg", "/*.gif",
                "/actuator/health").permitAll()
        // 其余全部要求登录（未认证返回 401）
        .anyRequest().authenticated())
.sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
```

**要点**：
- 静态资源必须**通配符**放行，不能硬编码页面清单（后面排障实录有大坑）；
- 页面 HTML 放行但 `/api/**` 全拦——"页面能打开、数据要登录"；
- 无 Session（STATELESS），认证状态全靠 JWT；
- `HttpStatusEntryPoint(UNAUTHORIZED)`：未认证统一返回 401 而非重定向（前后端分离标准做法）。

### 3.2 JwtService（生成 / 解析）

```java
SecretKey key = Keys.hmacShaKeyFor(secret.getBytes());  // secret 走环境变量 APP_JWT_SECRET
String token = Jwts.builder()
        .subject(username)          // 主题：用户名
        .claim("uid", userId)       // 自定义 claim：用户 id（CurrentUser 读这里）
        .claim("role", role)        // 自定义 claim：角色
        .issuedAt(new Date())
        .expiration(new Date(now + 24h))
        .signWith(key)              // 算法由密钥长度自动选择（≥256bit → HS384）
        .compact();

Claims claims = Jwts.parser().verifyWith(key).build()
        .parseSignedClaims(token).getPayload();
```

**坑（jjwt 0.12 的 API 变化）**：旧教程的 `Jwts.parser().setSigningKey()` 已废弃，0.12 必须 `parser().verifyWith(key).build().parseSignedClaims(token)`，算法 HS384 由密钥长度自动推断（不用显式指定）。

### 3.3 JwtAuthFilter（OncePerRequestFilter）

```java
String header = request.getHeader("Authorization");
if (header != null && header.startsWith("Bearer ")) {
    Claims claims = jwtService.parse(header.substring(7));
    UsernamePasswordAuthenticationToken auth = new UsernamePasswordAuthenticationToken(
            claims.getSubject(), null,
            List.of(new SimpleGrantedAuthority("ROLE_" + claims.get("role"))));
    auth.setDetails(claims);   // 关键：Claims 塞进 details，CurrentUser 从这里读 uid
    SecurityContextHolder.getContext().setAuthentication(auth);
}
filterChain.doFilter(request, response);
```

**设计要点**：
- 解析失败 → `clearContext()` 保持匿名，由 Security 规则兜底返回 401（不自己抛异常）；
- `claims` 放 `auth.getDetails()`：Controller/Service 里用 `SecurityContextHolder` 就能拿到 uid/role，不污染 principal。

### 3.4 CurrentUser（Service 层隔离核心工具）

```java
public static Long id() {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    if (auth != null && auth.getDetails() instanceof Claims claims) {
        return claims.get("uid", Long.class);
    }
    return null;   // 未登录（如工具线程）返回 null，调用方自行兜底
}
```

**为什么 Service 层不直接调 SecurityContext 而要包一层**：隔离逻辑散落各处时容易写错，统一走 `CurrentUser.id()` 一处收口——这也是"横切关注点收口"思想的体现。

## 4. AuthController：登录 / me / 注册开关 / Admin 初始化

### 4.1 端点一览

| 端点 | 作用 | 权限 |
|---|---|---|
| `POST /api/auth/login` | 用户名+密码 → token + 用户信息 | 放行 |
| `GET /api/auth/me` | 当前用户信息（前端导航栏用） | 登录 |
| `POST /api/auth/register` | 注册（**开关控制**） | 放行但 Service 校验 |
| `GET /api/auth/register/status` | 注册开关状态 | 登录 |

### 4.2 注册开关（重点：防直调）

```yaml
app:
  registration:
    enabled: false    # 默认关闭，页面无注册入口
```

```java
public Map<String, Object> register(String username, String password, String displayName) {
    // 开关校验放 Service 层——前端可以不做注册入口，但直调接口必须被拦
    if (!props.isRegistrationEnabled()) {
        throw new IllegalArgumentException("注册未开放");
    }
    // 用户名唯一 + 基础强度校验
    if (userMapper.selectOne(eq("username", username)) != null) {
        throw new IllegalArgumentException("用户名已存在");
    }
    ...
}
```

**为什么开关校验必须放 Service 层**：前端只是 UI 层，删掉注册按钮 ≠ 接口不可调。攻击者 curl 直调 `/api/auth/register` 就能绕过——所以**安全校验必须放在后端 Service 层**，前端藏按钮只是体验问题。

### 4.3 Admin 初始化（AdminInitializer）

```java
// 启动时：无 admin 则创建
if (userMapper.selectOne(eq("username", adminUsername)) == null) {
    UserDO admin = new UserDO();
    admin.setUsername(adminUsername);        // 环境变量 APP_ADMIN_USERNAME
    admin.setPassword(passwordEncoder.encode(adminPassword));  // 环境变量 APP_ADMIN_PASSWORD
    admin.setRole("ADMIN");
    userMapper.insert(admin);
}
```

**⚠️ 上线必改**：admin 默认密码 + JWT secret 都有 yml 默认值，演示/上线必须用环境变量 `APP_ADMIN_PASSWORD` / `APP_JWT_SECRET` 覆盖。

## 5. 用户隔离：6 类数据全按 userId

### 5.1 隔离模式（三种）

| 模式 | 做法 | 用在哪 |
|---|---|---|
| **写入带 userId** | 创建时 `setUserId(CurrentUser.id())` | 会话、文件、工单、日志、观测 |
| **查询按 userId 过滤** | `eq("user_id", CurrentUser.id())` | 会话列表、文件列表、工单列表、观测统计 |
| **越权校验** | selectById 后 `checkOwnership(d)`，非本人抛异常 | 打开历史、删除文件、向量化、删除会话 |

### 5.2 关键改造点（都在 Service 层收口）

- **ConversationService**：create 带 userId；list 过滤；touch/getHistory/delete 前校验归属；
- **ChatLogService**：append 带 userId（历史消息随会话隔离）；
- **RagFileService**：upload 带 userId + **用户内查重**（`findByHash` 加 userId 条件）+ list 过滤 + index/removeIndex/delete 前 `checkOwnership`；
- **AiCallLogObservationHandler**：落库带 userId——观测数据天然按用户隔离，ObsController 的 stats/logs SQL 全加 `WHERE user_id = #{userId}`；
- **AgentController.tasks / CreateTaskTool**：工单列表过滤 + 建单带 userId（工具方法里 SecurityContext 取不到就 catch 留 null，不阻断工具执行）。

### 5.3 种子知识库共享

`rag-docs` 种子文档（产品介绍/FAQ/请假制度）**全局共享**——它是"系统自带知识"，不属于任何用户。这是业务决策：隔离的是"用户产生的数据"，不是"系统提供的数据"。

## 6. 限流：RateLimitInterceptor（用户 + IP 双维度）

### 6.1 表结构

```sql
CREATE TABLE IF NOT EXISTS rate_limit_count (
    id          BIGINT       NOT NULL AUTO_INCREMENT,
    scope_type  VARCHAR(16)  NOT NULL,   -- USER / IP
    scope_value VARCHAR(128) NOT NULL,   -- 用户 id 或 IP
    action      VARCHAR(32)  NOT NULL,   -- CHAT / UPLOAD
    day         DATE         NOT NULL,
    count       INT          NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_rlc (scope_type, scope_value, action, day)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 6.2 核心：原子递增（防并发超卖）

```sql
INSERT INTO rate_limit_count (scope_type, scope_value, action, day, count)
VALUES (#{scopeType}, #{scopeValue}, #{action}, #{day}, 1)
ON DUPLICATE KEY UPDATE count = count + 1
```

**为什么必须用 `ON DUPLICATE KEY UPDATE`**：如果先 SELECT 再 UPDATE，并发请求会同时读到旧值 → 双双放行（竞态超限）。数据库唯一键 + 原子自增一步到位，天然防并发。

### 6.3 拦截器逻辑

```java
// 拦截 /api/chat、/api/chat/stream（CHAT）和 /api/rag/upload*（UPLOAD）
// 双维度都查：用户维度（登录了才算）+ IP 维度
// 任一超限 → 429 + 友好提示
// 未登录用户：只算 IP 维度（匿名也能限）
```

### 6.4 配额配置（演示量级）

```yaml
app:
  rate-limit:
    chat-per-user-per-day: 50      # 每用户每天 50 次聊天
    chat-per-ip-per-day: 100       # 每 IP 每天 100 次聊天
    upload-per-user-per-day: 5     # 每用户每天 5 次上传
    upload-per-ip-per-day: 10      # 每 IP 每天 10 次上传
```

**为什么双维度**：单 IP 限流防"换账号刷"，单用户限流防"多 IP 刷"——两个维度互相补漏。

## 7. 前端改造：login.html + auth.js

### 7.1 auth.js 三大职责

```js
// ① 未登录自动跳登录页（文件加载即执行——脚本在 <head> 同步加载，body 还没渲染 → 无闪烁）
(function () {
  if (!location.pathname.endsWith('login.html') && !getToken()) {
    location.replace('/login.html');   // replace 不污染浏览器历史
  }
})();

// ② monkey-patch fetch：所有 /api 请求自动带 token，401 自动跳登录
(function () {
  const _fetch = window.fetch;
  window.fetch = function (url, options) {
    // 带 token（登录/注册接口除外）
    // 收到 401 → clearToken() + location.href = '/login.html'
  };
})();

// ③ renderUserNav()：导航栏渲染 用户名 + 角色 + 退出按钮
```

**为什么 monkey-patch fetch 而不是改每个页面**：6+ 个页面的 fetch 调用点几十处，逐个加 header 极易漏。patch 一次全局生效——横切关注点的前端版。

### 7.2 页面接入

```html
<!-- <head> 里引入（同步加载，保证 patch 先于页面脚本） -->
<script src="auth.js"></script>
<!-- </body> 前 -->
<script>requireAuth(); renderUserNav();</script>
```

### 7.3 未登录跳转的完整链路

1. 打开 `index.html` → 页面 HTML 被 Security 放行（200）；
2. `<head>` 加载 `auth.js`（**必须也被放行**！否则脚本 401 加载失败，跳转逻辑失效——见排障实录）；
3. auth.js 同步执行：无 token → `location.replace('/login.html')`；
4. 登录后 token 存 localStorage，刷新任意页面直接放行。

## 8. 排障实录（每个都值得记）

### 8.1 假 401：路径前缀搞错了

**现象**：`/api/conversations` 全部 401，但 `/api/obs/stats` 200，JWT 解析看着也没问题。

**真相**：ChatController 类级注解是 `@RequestMapping("/api/chat")`，所以正确路径是 `/api/chat/conversations`。我测了不存在的路径，Security 对未知路径按"需认证"返回 401。**JWT 工作完全正常，纯属测试路径写错**。

**教训**：先确认 Controller 类级前缀再测；怀疑认证问题时先看 `JwtAuthFilter` 打一行诊断日志（uri + hasAuth），一次定位。

### 8.2 静态资源 401 坑（用户实测发现"未登录不跳转"）

**现象**：用户反馈"其他页面未登录不主动跳登录页"。检查发现 `auth.js` 请求返回 401。

**真相**：SecurityConfig 放行是**硬编码页面清单**（`/login.html, /index.html, /rag.html...` 逐页列出），`/auth.js` 和 `/ticket.html` 不在名单 → 页面 HTML 能打开但**引用的脚本被 401 拦截** → 加载失败 → 未登录跳转逻辑根本没执行。

**修复**：放行改为通配符 `/*.html, /*.js, /*.css, /*.ico, 图片后缀`——以后加任何静态资源不用再改 Security。

**教训**：**Security 放行静态资源必须用通配，硬编码页面清单迟早漏**。页面能打开 ≠ 页面功能正常，脚本被拦是最隐蔽的坏法。

### 8.3 后台任务进程被回收（环境限制，非代码问题）

**现象**：shell 里 `mvn spring-boot:run` 拉起的服务跨回合后被回收（Maven 包装进程结束 → Java 子进程连带被杀）。nohup 逃不掉，macOS 也没有 setsid。

**结论**：这是 WorkBuddy 后台任务机制的行为。**用户用 IDE 调试不受影响**；对外部署用 Docker（容器由 Docker 管理）。**工作约定：验证完不主动起服务，避免占端口影响用户 IDE。**

## 11. 阶段收获

1. **安全校验的"最后一公里"在后端**：前端藏按钮只是体验，Service 层开关校验才是安全边界——攻击者永远直调接口；
2. **隔离是横切关注点**：所有隔离逻辑在 Service 层收口到 `CurrentUser.id()`，一处拿用户、处处校验归属，比散落各处的取数方式可控得多；
3. **原子性是限流的生命线**：`INSERT ... ON DUPLICATE KEY UPDATE` 一个 SQL 搞定并发计数，SELECT-then-UPDATE 在高并发下必然超限；
4. **静态资源放行必须通配**：硬编码页面清单的教训是用"页面不跳转"的诡异 bug 换来的——页面能打开≠功能正常；
5. **无状态认证的取舍**：JWT 省了 session 管理，但 token 泄露 = 账号泄露，所以 secret 必须环境变量化、上线必换默认值。
