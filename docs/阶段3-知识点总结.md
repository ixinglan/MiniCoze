## 1. 主线（计划内）：RAG 检索增强

### 1.1 完整数据流

```
文档(PDF/Word/MD...) → DocumentReader → TokenTextSplitter(切片) → EmbeddingModel(bge-m3) → 向量库(add)
                                                                              ↓
用户问题 → 向量化问题 → 向量库 similaritySearch(topK) → 相关片段 → QuestionAnswerAdvisor 注入 prompt → LLM 回答
```

### 1.2 核心原语（Spring AI 1.1.2 实测 API，文档不准须以 jar 为准）

```java
// a. 向量库（内存版，最简单）
SimpleVectorStore vectorStore = SimpleVectorStore.builder(embeddingModel).build();

// b. 切片器（无参构造，带重叠窗口）
TokenTextSplitter splitter = new TokenTextSplitter();

// c. 文档构造器：注意是 (content, metadata) 两参，不是 (id, ...)
Document doc = new Document(text, Map.of("source", filename));

// d. 检索增强 Advisor：把相关片段自动注入 prompt
QuestionAnswerAdvisor advisor = QuestionAnswerAdvisor.builder(vectorStore)
        .searchRequest(SearchRequest.builder()
                .similarityThreshold(0.6).topK(4).build())
        .build();

// e. 挂 Advisor 的 RAG 客户端
ChatClient ragClient = ChatClient.builder(model)
        .defaultAdvisors(advisor, MessageChatMemoryAdvisor.builder(chatMemory).build())
        .build();
```

### 1.3 种子知识库（开箱即有内容可问）

`RagConfig` 用 `CommandLineRunner`（`loadRagDocuments`）在启动时扫描 `classpath:rag-docs/*`（.md/.txt），切片后 `vectorStore.add` 建索引。重启自动重建（需本地 Ollama bge-m3 在线）。

### 1.4 端点与演示页

- `GET /api/rag/stream`（SSE 流式）+ `POST /api/rag`（非流式）：RAG 问答
- `static/rag.html`：流式展示 + `[DONE]` 收尾标记（防误报失败）

## 2. 计划外扩展一：RAG 会话历史持久化 + chat/rag 隔离

### 2.1 会话历史持久化
RAG 页最初无历史。改造 `RagController` 注入 `ConversationService` + `ChatLogService`，完全照 `ChatController` 模式：发送前 `touch()` + `chatLogService.append(user)`，拿到完整回复后 `append(assistant)`。重写 `rag.html` 复用会话侧边栏（新建/切换/删除，历史从 `/api/chat/history` 拉）。

### 2.2 会话隔离（conversation.type）
聊天的 `conversation` 表加 `type VARCHAR(16) NOT NULL DEFAULT 'chat'` + 索引；`SchemaMigration`（CommandLineRunner）启动时查 `INFORMATION_SCHEMA` 幂等补列（老库 `CREATE TABLE IF NOT EXISTS` 会被跳过，仅改 schema 会报 Unknown column）。`listConversations(type)` 用 `Wrappers.query().eq("type", type)` 过滤。`rag.html` 固定传 `?type=rag`，当前会话 ID 存 `sessionStorage['ragCurrentConvId']` 与聊天页区分。

## 3. 计划外扩展二：RAG 文件管理（手动控制检索增强开关）

### 3.1 选型（用户拍板）
**Milvus** + **落盘存储** + **保留内置 rag-docs 自动索引**。

### 3.2 架构
- `rag_file` 表（元数据）：id / filename / content_type / size / storage_path / content_hash / status(uploaded|indexed) / doc_ids / 时间戳。文件本体落盘 `data/rag-files/`，**上传只落盘，点「向量化」才切片+解析+向量化+写库**——把"是否进知识库"的控制权交给用户。
- 新建 `RagFileDO` / `RagFileMapper` / `RagFileService` / `RagFileController`：
  - `POST /api/rag/files`（单）、`POST /api/rag/files/batch`（批量）上传
  - `GET /api/rag/files` 列表
  - `POST /api/rag/files/{id}/index` 手动向量化
  - `DELETE /api/rag/files/{id}/index` 移除索引（保留文件与记录）
  - `DELETE /api/rag/files/{id}` 彻底删除（移除索引+删文件+删记录）
  - `POST /api/rag/files/check` 上传前去重预检（见 §7）
- 手动向量化：`TikaDocumentReader` 解析（PDF/Word/Excel/PPT/TXT/MD 一把覆盖）→ `TokenTextSplitter` 切片 → bge-m3 向量化 → `vectorStore.add`；每个 chunk 用稳定 doc id + `fileId` 元数据，便于按文件移除（`vectorStore.delete(ids)`）。
- 前端 `rag.html`：**三栏布局**（左会话 / 中对话 / 右文件管理独立栏），选前预览 + 上传真实百分比进度 + 向量化进度。

### 3.3 向量库可切换（RagConfig）
`rag.vectorstore.type` = `memory`(默认 SimpleVectorStore) | `milvus`(MilvusVectorStore，维度 1024 对齐 bge-m3)。用 `spring-ai-milvus-store` 核心库**手动构建**（非 starter），避免无 Docker 时启动失败。`docker/milvus-standalone.yml` 一键起 etcd+minio+milvus。

> 📚 想系统了解向量数据库怎么选、各库 WebUI 与常见用法（Milvus / Qdrant / Weaviate / Chroma / pgvector / FAISS …），见文末 **附录 A**。

### 3.4 离线模式（ChatClientConfig）
`rag.offline.enabled=true` 时 `chatClient`/`ragClient` 生成切本地 Ollama LLM（注入 `ollamaChatModel`，`@Qualifier` 与 `deepSeekChatModel` 区分无冲突）。嵌入(Ollama)+向量库(本地/内存)+生成(Ollama) 全本地 = 可断网。

## 4. 计划外扩展三：向量化进度条（假动画 → 后端流式真进度）

### 4.1 演进
最初是"乐观 UI + CSS 不定长动画 + 静态文案"，并非真进度。用户要求改成真进度。

### 4.2 真进度实现
- `RagFileService.indexWithProgress(fileId, ProgressReporter)`：四阶段 `parse → split → 逐片段 embed(bge-m3) → write → done`，每完成一阶段/每嵌入一片经 `ProgressReporter.emit(Map)` 推事件（`stage/step/totalSteps/message/detail/percent/done/error`；percent 真实递增：parse 8→25 / split 30→50 / embed 50→75 逐片 / write 80→95 / done 100）。
- `RagFileController.index` 返回 `StreamingResponseBody`（`application/x-ndjson`），`ObjectMapper` 逐事件写一行 JSON 并 `flush`。
- 前端 `fetch` + `ReadableStream` 逐行解析 NDJSON，进度条宽度绑定后端 `percent`。
- `application.yml` 加 `spring.mvc.async.request-timeout: 600000` 防大文件被 Tomcat 异步超时断开。

## 5. 计划外扩展四：上传去重（SHA-256 内容指纹）

### 5.1 思路
比文件名/大小更准——**内容相同即视为重复，改名也逃不掉**。两层防护：
1. 前端预检：`crypto.subtle` 算哈希 → `POST /api/rag/files/check` 问后端哪些已存在 → 已上传过的直接 alert 跳过、只传新文件。
2. 后端权威：`RagFileService.upload` 算 SHA-256，表里已有同哈希记录则抛 `DuplicateFileException`，不落盘不建记录；单/批量捕获异常返回 `duplicate=true`。

### 5.2 表结构
`rag_file` 加 `content_hash CHAR(64)`（`schema.sql` 建表 + `SchemaMigration` 幂等 ALTER 兜底老库）。

## 6. 种子索引防重复（RagConfig 守卫）

`loadRagDocuments` 每次启动无条件 `add`。memory 模式本就空无妨；milvus 持久化会每次重复插入。加守卫：`milvus` 且 `!rag.seed.force-reindex` 时 `similaritySearch(topK=1)` 探空，非空则跳过。`force-reindex=true` 用于强制重建（文档已注明可能重复）。用 similaritySearch 而非 countEntities，是因为 milvus-sdk-java 2.5.8 **无 countEntities**；且 `initializeSchema(true)` 让启动即 `loadCollection`，探空 search 不会报未加载。

## 7. 踩的 API 坑（本次最值钱的踩坑 ⚠️）

全是 Spring AI 1.1.2 的真实行为，文档/WebFetch 不可全信：

1. **`MilvusVectorStore` 把 `doc_id` 硬编码 `VarChar(36)` 且不可配置**。原代码用 `fileId#序号`（UUID=36 + `#`+序号 = 38+）超 36 上限 → insert 报 `io.milvus.exception.ParamException: Type mismatch for field 'doc_id'`。修复：doc id 改「去横杠 UUID（32 字符）」，`fileId` 留 metadata 溯源/移除。milvus-sdk-java 是 store 直接依赖的 2.5.8（非 BOM 管理），上限无法靠升/降 SDK 绕过，只能约束 id 长度。
2. **`Document` API**：无 `setId`、取内容用 `getText()`（非 `getContent()`）；带 id 重建须用三参构造器 `new Document(id, text, metadata)`。
3. **`Document` 没有 `setEmbedding`/任何 embedding 字段**——向量只存向量库后端，`vectorStore.add` 内部用同一 `EmbeddingModel` 再嵌入一次（结果一致）。所以"手动嵌入"仅能驱动真实进度，无法避免 store 内部重复嵌入（demo 无功能影响，仅多一次耗时）。
4. **`MultipartFile.transferTo(File)` 在相对路径下被 Tomcat 解析到容器临时目录 → FileNotFound**。改用 `Files.copy(in, 绝对路径 target, REPLACE_EXISTING)`，且 `storageDir` 转绝对路径。
5. **`TokenTextSplitter` 无参构造**；`QuestionAnswerAdvisor` 包 `org.springframework.ai.chat.client.advisor.vectorstore.QuestionAnswerAdvisor`、`SimpleVectorStore` 包 `org.springframework.ai.vectorstore.SimpleVectorStore`（`document-reader-*` 在 1.1.2 未发布到 aliyun，故自读 classpath 文档构造 Document，零额外解析依赖）。

✅ 验证了修正后编译通过 + 端到端流程跑通（沙箱缺 MySQL/Milvus/Ollama 整套时用桩实现验证关键链路）。

## 9. 关键坑速查表 ⚠️

| 坑 | 根因 | 解法 |
|---|---|---|
| Milvus insert 报 `Type mismatch for field 'doc_id'` | `doc_id` 硬编码 `VarChar(36)`，doc id 超 36 | 用「去横杠 UUID（32 字符）」作 doc id |
| `Document` 编译/调用报错（setId / getContent） | 1.1.2 无 setId，内容用 getText() | `new Document(id, text, metadata)` 三参重建 |
| 手动 embedding 后仍被 store 再嵌入一次 | `Document` 无 embedding 字段，add 内部重嵌 | 接受（仅多一次耗时）；手动嵌入只为驱动进度 |
| 上传报 FileNotFound | `transferTo` 相对路径被 Tomcat 解析到临时目录 | `Files.copy(in, 绝对路径, REPLACE_EXISTING)` |
| 老库启动 `Unknown column 'type'`/`content_hash` | `CREATE TABLE IF NOT EXISTS` 被跳过 | `SchemaMigration` 幂等 ALTER 补列 |
| Milvus 每次启动重复插种子 | 持久化 + 无条件 add | `similaritySearch` 探空守卫（milvus 模式） |
| 大文件向量化被断开 | Tomcat 异步超时 | `spring.mvc.async.request-timeout: 600000` |
| 上传重复文件 | 仅前端提示不够 | 后端 SHA-256 去重 + `/check` 预检双保险 |

# 附录 A：向量数据库 —— 选型、原理与常见用法

> 阶段 3 实战里我们把向量库从内存 `SimpleVectorStore` 切到了 **Milvus**。这里把"向量数据库"这件事系统地补一层背景：它是什么、有哪些主流选手、各自优势 / WebUI / 用法，以及本项目为什么这么选。下方版本号、GitHub 热度、规模能力取 2025–2026 公开快照，仅作成熟度/活跃度判断，非精确基准。

## A.1 什么是向量数据库（为什么不用 MySQL / ES）

- **存的是高维向量（embedding），核心能力是"近似最近邻（ANN）"检索**，而非精确等值匹配。
- 与两类老朋友的本质区别：
  - 关系库（MySQL 等）：按行存、靠 `WHERE col = val` 精确匹配，不懂"语义相近"。
  - 搜索引擎（ES 等）：倒排索引 + 关键词 BM25，懂字面命中，不懂"意思相近"。
  - 向量库：把"问题"和"文档片段"都变成向量，按**余弦距离**找最相似的 topK 片段注入 prompt —— 这正是 RAG 的心脏。
- **库 vs 数据库**：FAISS 只是一块"内存 ANN 索引"，缺持久化、复制、多租户、权限；真上生产要"数据库"（Milvus / Qdrant / …）。一句话：**库给你索引，数据库给你全套运维。**

## A.2 核心概念（速览，原理点到为止）

- **维度（dimension）**：一个 embedding 的向量长度。常见：bge-m3 = 1024、MiniLM = 384、OpenAI text-embedding-3 = 1536。维度必须和你的 embedding 模型对齐（本项目 bge-m3 → 1024，故 Milvus 集合建 1024 维）。
- **距离度量**：`cosine`（最常用，与向量模长无关）、`L2`（欧氏距离）、`inner product`（内积，需先归一化）。选错度量，相似度就全乱。
- **索引类型**（召回 vs 速度权衡）：
  - `Flat`：暴力全量扫描，100% 召回但慢，适合小数据/精确场景。
  - `IVF`（Inverted File）：聚类分桶，先粗筛再精排，快但丢一点召回。
  - `HNSW`：分层可导航小世界图，现代主流，召回/延迟平衡最好（Milvus / Qdrant / Chroma 默认）。
  - `DiskANN`：磁盘索引，超大向量集低成本持久检索。
- **集合（collection）/ 分区（partition）/ 载荷（payload / metadata）**：向量 + 标量字段（如 `source`、`fileId`），既可检索又可做元数据过滤 —— 本项目"按文件移除索引"就是靠 `fileId` 这个 payload。

## A.3 常见向量数据库对比（2026 主流短期清单）

| 库 | 定位 | 开源协议 | 部署形态 | 典型规模 | 突出优势 | 适用场景 |
|---|---|---|---|---|---|---|
| **Milvus** | 大规模分布式专用库 | Apache 2.0 | 自托管 / K8s / Zilliz Cloud | 十亿~万亿 | 极致扩展、10+ 索引、GPU 加速、多租户 RBAC | 海量数据、多租户 SaaS、生产级 RAG |

## A.5 常见用法范式（落到 RAG 工程）

- **相似度检索**：`similaritySearch(queryVector, topK)` + 可选相似度阈值（如 cosine ≥ 0.6）过滤噪声片段。
- **混合检索（hybrid）**：dense 向量 + sparse（BM25 / SPLADE）双路召回再融合，提升关键词命中率（Qdrant / Weaviate / Milvus 均支持）。
- **元数据过滤**：检索同时按标量字段过滤，如 `source='xxx.pdf'` 或 `fileId=...` —— **本项目的 `fileId` 隔离正是此用法**，移除索引走 `vectorStore.delete(ids)` 按文件清。
- **多租户隔离**：用集合 / 分区 / 命名空间隔离不同用户或业务，避免数据串门。
- **批量 upsert + 增量更新**：首次批量写，后续按 id 更新/删除，不让索引无限膨胀（对应种子索引防重复守卫 §6）。
- **量化压缩**：binary / product quantization 大幅降内存（Qdrant 可降 90%+ RAM），大模型集必备。

## A.6 本项目视角：为什么从 memory 切到 Milvus

- **`SimpleVectorStore`（memory）**：纯内存、零依赖、demo 友好；但**重启即丢、不可多实例共享、无运维面板**。
- **`MilvusVectorStore`**：持久化、重启保留、支持海量、带 WebUI（Attu），契合"知识库工作台"长期沉淀私有资料的定位。
- **Spring AI 的 `VectorStore` 抽象统一了接口**：`SimpleVectorStore` / `MilvusVectorStore` 都是同一接口实现，靠 `rag.vectorstore.type` 切换 —— **业务代码（`RagFileService` 只依赖 `VectorStore`）零改动**，这就是抽象的价值。
- **编排**：`docker/milvus-standalone.yml` 一键起 `etcd + minio + milvus`（+Attu），本地即可获得生产级向量底座；无 Docker 时退回 `memory` 也能跑，零阻塞。
