## 0. 一句话心智模型

> **Tool Calling = 模型不直接算、不瞎编，而是"生成调用意图（tool_calls）" → 框架执行真实函数 → 把结果回填 → 模型据此组织回答。**
>
> 再补一句定位：阶段 0/1 是"聊天"，阶段 2 是"产出结构化对象"，阶段 3 是"让模型拥有你的知识"，阶段 4 是"让模型拥有你的技能"——Agent 从"嘴上说说"变成"真的能干"，这正是 Agent 工作台"理解需求 → 产出可执行动作"闭环的核心一步。

阶段 4 能力拼图（每个 = 一块可独立讲解的能力）：

| 能力 | 一句话 |
|---|---|
| 工具调用（主线） | `@Tool` 标注方法，模型自主调用，Spring AI 跑内部 tool-execution loop |
| 5 个工具 | 时间 / 计算器 / 天气(模拟) / 知识库检索 / 创建工单 |
| 工具调用可视化 | `ToolCallRecorder`(ThreadLocal) 100% 可靠捕获"调了哪些工具、传了啥" |
| agent 对话落库 | 复用 `ConversationService`(type=agent) + `ChatLogService`，挂记忆 Advisor |
| 工单落库 | 新建 `task_ticket` 表，`CreateTaskTool` 建单即写库，来源无关为阶段 6/7 留缝 |
| 离线兼容 | 工具本身是本地确定性逻辑，离线模式下 `agentClient` 切 Ollama 生成不受影响 |

## 1. 主线（计划内）：Tool Calling 机制

### 1.1 为什么需要工具调用

LLM 有三个先天短板，交给"确定性函数"更靠谱：

| 短板 | 例子 | 用工具解决 |
|---|---|---|
| 不知道"现在" | "今天几号？" | `DateTimeTool` 实时取系统时间 |
| 不擅长精确计算 | "1234.5 × 678.9 = ?" | `CalculatorTool` 用 Java 算，100% 准 |
| 不存在的"额外技能" | "查下北京天气" | `WeatherTool` / `RagQueryTool` 查外部或私有数据 |

**核心思想**：模型负责"理解意图 + 拆参数 + 读结果组织语言"，确定性逻辑交给真实代码。这既提升准确率，也让 Agent 能触达训练数据之外的事实与动作。

### 1.2 一次工具调用的完整数据流（tool-execution loop）

```
用户问题
  → ChatClient.call() 把 5 个工具的 JSON Schema 一并发给模型
  → 模型判断"需要算一下" → 返回 tool_calls[{name, arguments}]
  → Spring AI 在内部执行对应 @Tool 方法（真正的 Java 代码）
  → 把工具返回值回填成一条 "tool" 角色消息
  → 模型拿到结果，再生成最终自然语言回答
  → 最终 ChatResponse 通常只剩"最终答案"文本（中间的 tool_calls 可能被丢弃）
```

`defaultTools(...)` 注册后，这个 loop 由 Spring AI **自动驱动**，业务代码只需一次 `.call()`，不需要手写"解析 tool_calls → 执行 → 回填"的样板。

## 2. 核心原语（Spring AI 1.1.2 实测 API，文档不准须以 jar 为准）

### 2.1 声明一个工具：`@Tool` + `@ToolParam`

```java
@Service
public class CalculatorTool {

    private final ToolCallRecorder recorder;
    public CalculatorTool(ToolCallRecorder recorder) { this.recorder = recorder; }

    @Tool(description = "对两个数字做四则运算。operator 只能是 add/subtract/multiply/divide。")
    public String calculate(
            @ToolParam(description = "第一个操作数（数字）") double a,
            @ToolParam(description = "运算符") String operator,
            @ToolParam(description = "第二个操作数（数字）") double b) {
        recorder.record("calculate", Map.of("a", a, "operator", operator, "b", b)); // 可视化用
        return switch (operator) {                                              // 真正的确定性逻辑
            case "add"      -> String.valueOf(a + b);
            case "subtract" -> String.valueOf(a - b);
            // ... multiply / divide(除零保护) ...
        };
    }
}
```

要点：
- **`@Tool` 标在方法上**，`description` 是写给模型看的"说明书"——模型靠它判断是否该调、怎么调。**写好 description 比写好代码更重要**（直接决定调用准确率）。
- **`@ToolParam(description=...)`** 同样是给模型的参数说明；类型用简单 Java 类型（基本类型 / `String`），框架自动生成 JSON Schema。
- 工具类必须是 **Spring Bean**（`@Service`/`@Component`），Spring AI 才能扫描到里面的 `@Tool` 方法。

### 2.2 注册工具：`defaultTools(bean...)`

```java
@Bean
public ChatClient agentClient(ChatModel deepSeek, ChatModel ollama,
        DateTimeTool dateTimeTool, CalculatorTool calculatorTool,
        WeatherTool weatherTool, RagQueryTool ragQueryTool, CreateTaskTool createTaskTool,
        ChatMemory chatMemory, @Value("${rag.offline.enabled:false}") boolean offline) {
    ChatModel gen = offline ? ollama : deepSeek;
    return ChatClient.builder(gen)
        .defaultSystem("你是一个具备工具调用能力的 AI 助手……请根据用户需求自主判断是否需要调用工具……")
        .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())   // 阶段 4 补全：记忆
        .defaultTools(dateTimeTool, calculatorTool, weatherTool, ragQueryTool, createTaskTool)
        .build();
}
```

`defaultTools(bean1, bean2, ...)` 接收的是**工具 Bean 实例**，Spring AI 会扫描每个 Bean 里所有 `@Tool` 方法、自动生成 Schema 交给模型。

### 2.3 发起调用（控制器里）

```java
recorder.begin(cid);                       // 重置 ThreadLocal 调用记录 + 携带会话 ID
try {
    ChatResponse response = agentClient.prompt()
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, cid))   // 记忆隔离到本次会话
        .user(message)
        .call()
        .chatResponse();
    String answer = response.getResult().getOutput().getText();
    List<Map<String, Object>> toolCalls = recorder.collect();      // 拿可视化数据
    // ... 返回 {answer, toolCalls, conversationId}
} finally {
    recorder.clear();                     // 释放 ThreadLocal，防内存泄漏
}
```

## 3. 五个工具逐一讲解（含各自踩坑）

| # | 工具 | 解决什么短板 | 要点 |
|---|---|---|---|
| 1 | `DateTimeTool` | 模型不知道实时时间 | `LocalDateTime.now()` 格式化返回，每次都 `record` 可视化 |
| 2 | `CalculatorTool` | LLM 算数易错 | `operator` 限定枚举字符串，除零保护 |
| 3 | `WeatherTool` | 模型没有天气数据 | 演示用**稳定伪随机**（同城市结果一致），真实场景换第三方 API |
| 4 | `RagQueryTool` | 模型不懂你的私有资料 | 复用阶段 3 的 `VectorStore`，把 RAG 从"被动注入"变"模型主动调" |
| 5 | `CreateTaskTool` | 模型只能说、不能落地 | 复用阶段 2 的 `TaskTicket` 结构，建单即写库，体现"动手" |

**工具 4 `RagQueryTool` 的妙处**：阶段 3 用 `QuestionAnswerAdvisor` 让资料"被动注入"——模型别无选择必须基于资料答。阶段 4 把它包成工具后，模型可以**自主判断"这个问题我要不要查资料"**，甚至结合其它工具多步推理。这是 Agent 编排（阶段 6）里"模型决定动作"思想的雏形。

**工具 5 `CreateTaskTool` 的闭环意义**：阶段 2 学了"把自然语言解析成结构化对象"，阶段 4 让模型在理解意图后**主动把一件事落成一张库里工单**。Agent 不再是"嘴上答应"，而是真的"建了一条记录"。

```java
// CreateTaskTool 关键逻辑（落库版）
TaskTicketDO t = new TaskTicketDO();
t.setId(UUID.randomUUID().toString());
t.setTitle(title); t.setCategory(category); t.setPriority(priority);
t.setDescription(description);
t.setStatus("open");                 // 默认待办
t.setSource("agent");                // 来源：当前 Agent 工具
t.setConversationId(recorder.getConversationId());  // 关联到触发它的会话
t.setTags("[]");
taskTicketMapper.insert(t);
```

## 4. 工具调用可视化：`ToolCallRecorder`（本阶段最关键的坑）

### 4.1 为什么需要它（踩坑起点）

理想很丰满：从 `ChatResponse` 里直接解析 `toolCalls` 给前端展示"模型调了哪些工具"。现实很骨感——

- **`ChatResponseMetadata` 在 Spring AI 1.1.2 里没有 `getToolCalls()` 方法**（很多旧教程写 `response.getMetadata().getToolCalls()`，编译都过不了）。
- `toolCalls` 实际在 `AssistantMessage.getToolCalls()`（`AssistantMessage$ToolCall` record：id/type/name/arguments）。
- 但默认 `call()` 跑完内部 tool-execution loop 后，**最终 `ChatResponse` 往往只剩"最终文本"，中间的 `toolCalls` 未必保留**。直接解析响应拿调用明细非常脆弱、时有时无。

### 4.2 解法：ThreadLocal 主动记录（100% 可靠）

```java
@Component
public class ToolCallRecorder {
    private final ThreadLocal<List<Map<String, Object>>> holder = ThreadLocal.withInitial(ArrayList::new);
    private final ThreadLocal<String> conversationIdHolder = new ThreadLocal<>();

    public void begin(String conversationId) {                 // 每个请求开始：重置 + 记会话
        holder.set(new ArrayList<>());
        conversationIdHolder.set(conversationId);
    }
    public void record(String name, Map<String, Object> params) {  // 每个 @Tool 方法第一行调用
        Map<String, Object> entry = new LinkedHashMap<>();
        entry.put("name", name); entry.put("params", params);
        holder.get().add(entry);
    }
    public List<Map<String, Object>> collect() { return new ArrayList<>(holder.get()); } // 给前端
    public void clear() { holder.remove(); conversationIdHolder.remove(); }              // 防泄漏
}
```

设计要点：
- **每个 `@Tool` 方法第一行 `recorder.record(name, params)`**，在真实逻辑执行前就记一笔——确保哪怕工具抛异常也能看到"调了"。
- **用 `ThreadLocal` 而非全局 `List`**：Web 每个请求跑在独立线程，天然隔离并发请求，互不污染。
- **`finally { recorder.clear() }`**：请求结束必须清掉 ThreadLocal，否则线程池复用时旧数据残留 → 内存泄漏 / 串数据。
- **额外职责：携带 `conversationId`**。工具方法签名里拿不到请求级 `conversationId`，通过 ThreadLocal 在 `begin(cid)` 时传入，`CreateTaskTool` 落库时 `recorder.getConversationId()` 取出关联——避免了为 `@Tool` 方法硬加参数、改动工具签名。

## 5. 阶段 4 补全：落库（对话 + 工单）

### 5.1 agent 对话落库（零新表，复用既有基建）

`agentClient` 挂上 `MessageChatMemoryAdvisor(chatMemory)`（与 chat/rag 同一套 JDBC 记忆仓库，按 `conversationId` 隔离）。`AgentController.chat` 复用既有服务：

1. `conversationId` 缺省 → `conversationService.createConversation("agent")` 新建 **type=agent** 会话；
2. `conversationService.touch(cid, message)` 刷新排序 + 首句设标题；
3. `chatLogService.append(cid, "user"/"assistant", text)` 写完整历史；
4. 通过 `ChatMemory.CONVERSATION_ID` 让记忆 Advisor 读写对应会话。

**决策**：会话 UI 与阶段 1/3 共用 `conversation`/`chat_log` 表，仅用 `type` 字段区分，不另建表——agent 页左侧会话列表直接复用 `/api/chat/conversations?type=agent`。

### 5.2 工单落库（新建 `task_ticket` 表，来源无关）

```sql
CREATE TABLE IF NOT EXISTS task_ticket (
  id VARCHAR(36) PRIMARY KEY,
  title VARCHAR(255),
  category VARCHAR(64),
  priority VARCHAR(16),
  due_date VARCHAR(32),
  tags TEXT,                  -- 存 JSON 数组字符串，读取时再解析
  description TEXT,
  need_follow_up TINYINT(1),
  status VARCHAR(16),         -- open / done（后续阶段更新）
  source VARCHAR(32),         -- agent / mcp(阶段7) / subagent(阶段6)
  conversation_id VARCHAR(36),-- 关联触发它的会话，便于溯源
  created_at DATETIME,
  updated_at DATETIME
);
```

`TaskTicketDO`（`MyBatis-Plus`）与阶段 2 的 `TaskTicket`（纯结构化抽取目标）**解耦**：DO 负责落库，额外带 `status`/`source`/`conversation_id`/时间戳等生命周期字段。`/api/agent/tasks` 改从这张表读（按 `created_at` 倒序），不再用内存列表，重启不丢。

**为后续阶段留的缝**：`source` 字段设计为来源无关（agent / mcp / subagent），`status` 预留 `done`——阶段 6 子智能体、阶段 7 MCP 工具产出的工单都能统一落这张表，无需改结构。

## 6. 踩坑大全（1.1.2 实测）

| 坑 | 现象 | 根因（1.1.2） | 正确写法 |
|---|---|---|---|
| `@Tool` 注解位置 | 旧教程让引 `spring-ai-commons` | `@Tool`/`@ToolParam` 在 **`spring-ai-model`** 模块（本项目已依赖 model，无需加包） | 直接 `import org.springframework.ai.tool.annotation.Tool` |
| `getToolCalls()` 不存在 | `response.getMetadata().getToolCalls()` 编译失败 | `ChatResponseMetadata` 1.1.2 无该方法；toolCalls 在 `AssistantMessage`，且 loop 后不保留 | 用 `ToolCallRecorder` 主动记录 |
| 并发调用串数据 | 多请求下 toolCalls 错乱 | 若用全局 `List` 存记录，线程间互相污染 | `ThreadLocal` + `finally clear()` |
| 工具拿不到 conversationId | `@Tool` 方法无法加请求参数 | 工具签名是给模型看的，不能随便加参数 | `ToolCallRecorder` 的 ThreadLocal 传 `conversationId` |
| Lambda 捕获非 final | 编译报错 variable used in lambda should be final | `conversationId` 在 if/else 里赋值，非 final | 抽成 final `cid` 再进 lambda |

> 版本提醒（复盘前次联网核实）：以上坑**不是版本 bug**，而是框架设计使然（`Document`/`ToolCall` 的返回结构、工具执行 loop 行为）。升 Spring AI 2.0 也基本如此，现有 `ToolCallRecorder` 写法即"正确写法"，不必等升级。

## 7. 端到端数据流（agent 一次问答）

```
浏览器(agent.html)
  → POST /api/agent/chat {message, conversationId?}
  → AgentController:
      创建/复用 type=agent 会话 → touch → 写 chat_log(user)
      recorder.begin(cid)
      agentClient.prompt().advisors(CONVERSATION_ID=cid).user(message).call()
        └─ Spring AI 内部 loop：
            模型 → tool_calls → 执行 @Tool(每个都 recorder.record) → 回填 → 模型答
      collect toolCalls → 写 chat_log(assistant)
      return {answer, toolCalls, conversationId}
  → 前端分步高亮"调用了哪些工具 + 参数"
  （若模型调了 createTask → task_ticket 表新增一行，/api/agent/tasks 可见）
```
