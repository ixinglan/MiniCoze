# 阶段 1 知识点总结 —— 多轮记忆、持久化与前端会话管理

> 阶段 1 目标：让助手"记得住"——从内存滑动窗口，一路演进到 MySQL 持久化、前端会话列表、双表分离。
> 本阶段最大特点是：**主线（记忆三件套）之外，踩出了一连串计划外的工程化改造**，每一处都是真问题驱动。

## 0. 一句话心智模型

> **ChatMemory 决定"模型记什么"，Advisor 决定"何时注入/截取记忆"，ChatMemoryRepository 决定"记忆存在哪"。三者解耦，业务代码几乎不动就能获得多轮能力。**

再补一句演进链路：

> 内存窗口 → 持久化(MySQL) → 完整日志(chat_log)。每一步都在解决"窗口裁剪会不会丢数据"这个核心焦虑。

## 1. 主线（计划内）：记忆三件套

### 1.1 ChatMemory 抽象
Spring AI 用 `ChatMemory` 接口统一表示"一个会话的历史消息容器"。它不关心存哪（内存/MySQL/Redis 都行），只定义行为：`add` / `get` / `clear`。

### 1.2 MessageWindowChatMemory 滑动窗口
实际用的是 `MessageWindowChatMemory`，带一个滑动窗口：

```java
ChatMemory chatMemory = MessageWindowChatMemory.builder()
        .chatMemoryRepository(new InMemoryChatMemoryRepository())
        .maxMessages(20)   // 窗口大小 = 20 条 message
        .build();
```

⚠️ **maxMessages 是"条数"不是"轮数"**：一问一答 = 2 条 message，所以 20 条 = **10 轮问答**。第 11 轮开始时，最早的 1 轮就被悄悄裁掉。

### 1.3 Advisor：记忆怎么自动生效
`MessageChatMemoryAdvisor` 把 ChatMemory 挂到 ChatClient 上：

```java
ChatClient client = ChatClient.builder(model)
        .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
        .build();
```

Advisor 本质是一个**责任链**，包在 ChatModel 外层。每次请求：
- **before**：从 ChatMemory 按 conversationId 取出历史，注入 prompt
- **after**：把本次 user + assistant 消息写回 ChatMemory

（Spring AI 1.1.2 的 Advisor API 已重构为 `ChatClientRequest`/`adviseCall` + `before`/`after`，不是老版的 `AdvisedRequest`/`aroundCall`。）

### 1.4 按会话隔离：ChatMemory.CONVERSATION_ID
多会话并存靠一个 key 区分。在调用时通过 advisor 参数传入：

```java
chatClient.prompt()
        .user(message)
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
        .call()
        .content();
```

`MessageChatMemoryAdvisor` 内部用 `ChatMemory.CONVERSATION_ID` 这个常量键从请求上下文读会话 ID。（已查源码 + javap 核验过。）

### 1.5 显式依赖 spring-ai-model / spring-ai-client-chat
阶段 0 这俩是传递依赖。阶段 1 因为直接用到 `ChatMemory`、`MessageWindowChatMemory`、`MessageChatMemoryAdvisor` 等类型，显式声明到 pom（版本由 spring-ai-bom 管，不用写 version）：

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-model</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-client-chat</artifactId>
</dependency>
```

💡 为什么显式引入：避免以后某个 starter 升级后传递依赖消失，编译突然挂掉。显式声明 = 依赖意图可见、稳定。

## 2. 计划外改造一：前端刷新后聊天记录"丢失"

**现象**：切到新对话再刷新页面，之前的聊天气泡不见了（但后端记忆其实正常）。

**根因**：会话 ID 存 `sessionStorage`（刷新保留，后端记忆正确），但消息气泡是每次加载重新渲染的 DOM。刷新后 `#chat` 容器是空的，用户"看不到历史"。

**修复**（`static/index.html`）：
- 新增 `messages` 数组 + `sessionStorage['chatMsgs']` 持久化
- 初始化时 `loadMessages()` + `renderAll()` 恢复历史
- send 时 user/bot 消息入数组并 `saveMessages()`；流式 `onmessage` 累加 bot 文本后保存
- `newChat()` 同时清 `chatMsgs`
- 渲染改用 `span.textContent`（**自动转义 HTML**，替代手写 escapeHtml，顺手防 XSS）

💡 这其实是"前端状态持久化"的入门——后来被 MySQL 方案取代，但 `textContent` 防 XSS 的做法保留到了最终版。

## 3. 计划外改造二：InMemory → MySQL 持久化 + 前端会话列表面板

**需求（你提的）**：记忆改用 MySQL（localhost:3306 / 库 mini_coze），自建表；前端不再用 sessionStorage 存消息，统一按 conversationId 从后端拉历史；"新对话"不删旧记录，改成左侧会话列表、可逐个删除、只有点删除才真删。账号 root/123456 直写配置（不走环境变量）。

### 3.1 表结构（schema.sql）
- `chat_memory`（conversation_id VARCHAR(64) + message_index INT 联合主键，message_type、content、metadata、created_at）——**整窗替换**
- `conversation`（id PK、title、created_at、updated_at ON UPDATE）——左侧栏元数据

### 3.2 自定义 Repository
`MysqlChatMemoryRepository implements ChatMemoryRepository`：
- `saveAll` = 先 `DELETE` 该会话全行，再按 index 批量 `INSERT`（整窗替换，所以超窗老消息被物理删除，见第 6 节）
- `findByConversationId` = 按 `message_index` 升序重建 `Message`
- `findConversationIds` = `SELECT DISTINCT conversation_id`

### 3.3 ⚠️ 三个 Spring AI 1.1.2 的硬核坑（本项目最值钱的踩坑）
1. **Message 取文本方法是 `getText()`，不是 `getContent()`**。它在 `org.springframework.ai.content.Content` 接口（spring-ai-commons jar）。踩坑过程：最初写 `getContent()` 编译直接挂，查源码才确认。
2. **消息类没有 `(String, Map)` 构造器**。还原历史时只能用 content-only 方式重建 Message（metadata 仅存数据库、不还原进对象）。
3. **类型序列化用 `MessageType.fromValue()` / `getValue()`**。存库时存 `messageType.getValue()`（大写如 USER/ASSISTANT），读出来用 `MessageType.fromValue()` 还原。

### 3.4 ConversationService / ChatController 改造
- `ConversationService`：create / list / getHistory / delete + `touch()`（刷新 `updated_at`、首句前 30 字设标题）
- `ChatController`：去掉 `/clear` 与 ChatMemory 直接注入；新增 `GET/POST /api/chat/conversations`、`GET /api/chat/history`、`DELETE /api/chat/conversation`；stream/chat 发送时调 `touch(conversationId, message)`
- `ChatClientConfig.chatMemory` 注入 `JdbcTemplate`，`new MysqlChatMemoryRepository(jdbcTemplate)`
- `index.html` 重写：左侧会话栏（新建/切换/删除），历史从 `/api/chat/history` 拉；`sessionStorage` 仅存当前 `conversationId`

💡 这一步把"记忆"从玩具级（刷新就丢）升级成产品级（持久化 + 多会话管理）。

## 4. 计划外改造三：原生 JDBC → MyBatis-Plus

**需求（你提的）**：把所有原生 jdbc 操作 SQL 的地方改成 MyBatis Plus 方式。

**改动**：
- `pom.xml`：移除 `spring-boot-starter-jdbc`，新增 `mybatis-plus-boot-starter`（版本属性 `mybatis-plus.version=3.5.17`）
- 新增 `entity/ChatMemoryDO`、`entity/ConversationDO`（Lombok @Data，@TableName 映射）
- 新增 `mapper/ChatMemoryMapper`、`ConversationMapper`（extends BaseMapper<T> + @Mapper）+ `config/MybatisPlusConfig`(@MapperScan("com.ai.aiworkshop.mapper"))
- `MysqlChatMemoryRepository` / `ConversationService`：去掉 JdbcTemplate，改用 Mapper + `QueryWrapper`
- `application.yml`：加 `mybatis-plus.configuration.map-underscore-to-camel-case=true`
- `schema.sql` 的 DDL 初始化脚本保留（它负责建表，与业务代码解耦）

⚠️ **复合主键处理**：`chat_memory` 是 (conversation_id, message_index) 联合主键。MyBatis-Plus 的 `@TableId` 只能标一个字段，所以 `conversation_id` 当 `@TableId(type=INPUT)`、`message_index` 当普通列。这是 MyBatis-Plus 处理"非自增复合主键"的惯用手法。

## 5. 修复：启动 Invalid bean definition 'chatMemoryMapper'

**现象**：引入 MyBatis-Plus 后启动报
```
Invalid bean definition with name 'chatMemoryMapper':
Invalid value type for attribute 'factoryBeanObjectType': java.lang.String
```

**根因（关键）**：`mybatis-plus-boot-starter` 写死依赖 `mybatis-spring:2.1.2`（Spring 5 时代）。老版本注册 Mapper 时往 `BeanDefinition.factoryBeanObjectType` 写 `String`，而 Spring Boot 3.5 用 **Spring 6.2**，该属性要求 `Class` 类型 → `getTypeForFactoryBean` 抛异常（被 sql.init 触发）。

**修复**（`pom.xml` 的 `dependencyManagement`）：
```xml
<dependency>
    <groupId>org.mybatis</groupId>
    <artifactId>mybatis-spring</artifactId>
    <version>3.0.6</version>   <!-- 适配 Spring 6.2 -->
</dependency>
```
顺带把 `mybatis-plus.version` 升到 `3.5.17`。

✅ 验证：本地 `mvn spring-boot:run` 完整启动成功（`Started AiWorkshopApplication`），HikariPool 连上 mini_coze，Mapper 注入全通。

> 💡 **经验沉淀（必记）**：Spring Boot 3.5 项目用 MyBatis-Plus，务必在 dependencyManagement 锁 `mybatis-spring` 到 3.0.x，否则 starter 默认的 2.1.2 必炸 Mapper 注册。这是版本矩阵问题，不是偶发。

## 6. 计划外改造四：双表分离（chat_memory 喂模型 + chat_log 完整日志）

**触发问题（你问的）**：`maxMessages(20)` 窗口超 20 条后，会自动删 MySQL 里的数据吗？
**结论：会，而且是物理删除。** 因为 `MysqlChatMemoryRepository.saveAll` 是整窗替换（DELETE 全部 + 重新 INSERT），超窗老消息直接从库里消失。前端 `/api/chat/history` 读的是这张被裁剪的表 → **超 10 轮对话后历史"缺头"**。

**方案：双表分离**
| 表 | 职责 | 是否裁剪 |
|---|---|---|
| `chat_memory` | 喂模型的滑动窗口（省 token） | ✅ 超窗被裁剪 |
| `chat_log` | 给人回看的完整日志（append-only 永留） | ❌ 永不删 |

**改动**：
- `schema.sql`：新增 `chat_log(id 自增, conversation_id, role, content, created_at, 联合索引)`
- 新增 `entity/ChatLogDO`、`mapper/ChatLogMapper`、`service/ChatLogService`（append / getFullHistory 按 created_at 升序 / deleteByConversationId）
- `ConversationService.getHistory` 改读 `chat_log`（不再读被裁剪的 chat_memory）；`deleteConversation` 级联删 chat_log
- `ChatController` 的 stream/chat 端点：发送时 append user、拿到完整 assistant 回复后 append assistant
- **前端 `index.html` 一行没动**——`history` 返回的仍是 `{role, content}` 结构，chat_log 沿用，完全兼容

✅ 验证：`mvn -q compile` 通过；占位 key 后台 `spring-boot:run` 启动成功；`/api/chat/history` 返回 HTTP 200 证明 chat_log 表已自动建好、查询链路打通。

⚠️ 注意：`spring-boot:run` 这次是随机端口（Maven 插件行为），你本地 `java -jar` 仍是 **9999**，配置没变。

### 6.1 迁移 SQL（救回旧数据）
`src/main/resources/migrate_chat_memory_to_chat_log.sql`：
- 把 `chat_memory` 当前残留数据（每会话最多 20 条）同步进 `chat_log`
- `INSERT ... SELECT ... WHERE NOT EXISTS(...)` 幂等，可反复跑不翻倍
- `created_at + INTERVAL message_index SECOND` 重排，保证同会话内时间严格递增、回看顺序不乱
- ⚠️ **只能救回"现在还留在 chat_memory 里的"数据**；更早被整窗替换删掉的，SQL 层已救不回

## 8. 关键坑速查表 ⚠️

| 坑 | 根因 | 解法 |
|---|---|---|
| `Message.getContent()` 编译挂 | Spring AI 1.1.2 方法名是 `getText()` | 用 `getText()`（Content 接口，spring-ai-commons） |
| 消息无 (String,Map) 构造器 | 1.1.2 实现限制 | content-only 重建 Message，metadata 仅存不还原 |
| 启动 `Invalid bean definition 'chatMemoryMapper'` | mybatis-spring 2.1.2 不适配 Spring 6.2 | dependencyManagement 锁 mybatis-spring 3.0.6 |
| 超窗历史"缺头" | saveAll 整窗替换物理删除老消息 | 双表分离：chat_log append-only |
| Ollama 抢注 ChatModel | Ollama starter 默认注册 ChatModel | `spring.ai.ollama.chat.enabled=false`（阶段 0 已记） |
| MyBatis-Plus 复合主键 | @TableId 只能一个 | conversation_id 当 @TableId(INPUT)，message_index 普通列 |

## 10. 阶段 1 → 阶段 2 衔接

阶段 1 解决了"助手记得住、历史看得全"。但模型返回的是**自由文本**——接下来要做的是**结构化输出**：

- `PromptTemplate`：把提示词模板化（占位符填参数）
- `BeanOutputConverter`：教模型把一句话转成规整的 Java 对象（工单/摘要/实体），直接落库或接 API

把"非结构化文本 → 结构化对象"打通，你的 Agent 工作台才真正能"干活"而不只是"聊天"。
