# 阶段 8 知识点总结 —— 工程化三件套：可观测 + Guardrails + Docker 部署

> 学习主线：把"能用的产品"变成"敢上线的产品"——先看得见（可观测），再拦得住（护栏），最后装得走（容器化）。

## 0. 一句话心智模型

**工程化 = 三层防线**：**可观测**（调用全链路可追溯：自建落库 + Langfuse 平台）→ **Guardrails**（输入输出两道闸：敏感词/越狱拦截 + PII 脱敏）→ **Docker**（一键打包部署）。三者共用同一个 Spring 机制：**Advisor / Observation 这类"横切点"**——业务代码零侵入，能力自动叠加。

## 1. 可观测性概念：为什么 LLM 应用更需要观测

### 1.1 传统可观测三支柱 vs LLM 特殊性

传统（Web 应用）观测三支柱：**Metrics（指标）/ Logs（日志）/ Traces（链路）**。LLM 应用额外多两个刚需维度：

| 维度 | 关注点 | 传统方案 | LLM 特殊性 |
|---|---|---|---|
| **Token 计量** | 每次调用的输入/输出 token → 成本 | 无对应 | 每轮对话都是钱，必须按模型/会话统计 |
| **内容审计** | 用户问了什么、模型回了什么 | 通常不记 | 合规需要（Prompt 注入、敏感内容） |
| **质量评估** | 回答好不好 | 无 | 需要人/AI 评审（Langfuse 的 evaluation） |

所以 LLM 可观测 = 传统 Tracing（耗时/模型/错误）+ **token 计量** + **内容记录**。

### 1.2 本项目双轨方案

```
                     ┌─ 自建：Observation → MySQL ai_call_log → obs.html 监控页（零依赖，讲清机制）
每次 LLM 调用 ──►  Observation
                     └─ Langfuse：Observation → Micrometer → OTel Span → OTLP → Langfuse（平台视角）
```

- **自建**：最能讲清 Spring AI 的观测机制，零外部依赖，秒级可查；
- **Langfuse**：开源 LLM 观测平台（对标 LangSmith），自托管后 UI 看 Trace、算成本、做评估。

## 2. Spring AI 1.1.2 的 Observation 机制（核心概念）

### 2.1 四件套：Observation / Context / Handler / Convention

Spring AI 的观测基于 **Micrometer Observation**（Spring Boot 3 标准）：

| 概念 | 作用 | 本项目对应的类 |
|---|---|---|
| **Observation** | 一次"可观测的操作"（如一次模型调用） | 内部自动创建，无需手写 |
| **Context** | 这次操作的数据载体（请求/响应/错误） | `ChatModelObservationContext` |
| **Handler** | 观察者，订阅 Context 的 onStart/onStop/onError | 我们写的 `AiCallLogObservationHandler` |
| **Convention** | 把 Context 转成指标标签/span 属性的命名规则 | 框架内置（`gen_ai.*` 语义约定） |

**数据流**：`ChatModel 调用 → 创建 Observation(Context) → ObservationRegistry 分发给所有 Handler → onStart / onStop 被回调`。

### 2.2 为什么"注册一个 Spring Bean 就能自动生效"

```java
@Component
public class AiCallLogObservationHandler implements ObservationHandler<ChatModelObservationContext> {
    // 无任何手动注册——ObservationRegistry 会自动收集容器里所有 ObservationHandler Bean
}
```

Spring Boot Actuator 的 `ObservationAutoConfiguration` 创建 `ObservationRegistry`，并自动收集所有 `ObservationHandler` Bean。**这就是"横切"：加了 Bean，所有 ChatModel 调用自动被记录，业务代码零改动。**

> ⚠️ **前置依赖**：必须加 `spring-boot-starter-actuator`——`ObservationRegistry` 的自动配置在 Actuator 里。没有它，Handler 永远不会被调用。

### 2.3 关键 API（反编译核实）

```java
// Handler 核心两个方法
@Override
public boolean supportsContext(Observation.Context context) {
    return context instanceof ChatModelObservationContext;  // 只关心聊天模型
}

@Override
public void onStart(ChatModelObservationContext context) {
    context.put("startTime", System.currentTimeMillis());   // Context 自带 KV 存储
}

@Override
public void onStop(ChatModelObservationContext context) {
    AiOperationMetadata meta = context.getOperationMetadata();     // provider / operationType
    ChatResponse response = context.getResponse();                 // 响应侧
    ChatResponseMetadata md = response.getMetadata();
    md.getModel();            // 模型名：deepseek-v4-flash
    md.getUsage();            // Usage: getPromptTokens / getCompletionTokens / getTotalTokens
    Throwable error = context.getError();                          // 错误（onStop 统一收口）
    Long start = context.get("startTime");                         // 取 onStart 存的时间算耗时
}
```

**设计要点**：
- **onStop 而不是 onError**：Observation 生命周期 onStart →（成败）→ onStop **必然触发**，错误通过 `context.getError()` 拿，成功失败统一收口最干净；
- **耗时**：`onStart` 用 `context.put("startTime", ...)` 存，`onStop` 取出相减——Context 自带 KV，不需要外部 Map；
- **稳定性**：Handler 落库任何异常只 `log.warn` 不抛——**观测绝不允许影响主业务**。

### 2.4 自建落库清单

| 文件 | 作用 |
|---|---|
| `AiCallLogObservationHandler` | 观测核心：onStop 组装 `ai_call_log` 落库 |
| `AiCallLogDO` / `AiCallLogMapper` | MyBatis-Plus 实体 + `@Select` 聚合统计 SQL |
| `ObsController` | `/api/obs/stats`（KPI + 模型分布 + 近 7 天趋势）+ `/api/obs/logs`（明细） |
| `obs.html` | 监控页（KPI 卡片 / 模型分布条形 / 趋势柱状 / 明细表） |
| `schema.sql` | `ai_call_log` 建表（append-only） |

**验证亮点**：Agent 工具循环的**每次 LLM 调用独立成条**（第一轮工具决策 1151+48 tok、第二轮总结 2375+82 tok）——工具循环过程在观测里一目了然。

## 3. OTel + Langfuse 接入

### 3.1 依赖（版本由 Boot 3.5.11 管理，不写 version）

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-otlp</artifactId>
</dependency>
```

**链路**：Spring AI 的 Observation（Micrometer 层）→ `micrometer-tracing-bridge-otel` 把 Observation 转成 **OTel Span** → `opentelemetry-exporter-otlp` 通过 OTLP 协议导出 → Langfuse 摄入。

### 3.2 配置逐条拆解（application.yml）

```yaml
management:
  tracing:
    sampling:
      probability: 1.0        # 采样率：本地 100%；生产建议 0.1（错误 span 绕过采样强制记录）
  otlp:
    tracing:
      endpoint: ${LANGFUSE_OTLP_ENDPOINT:http://localhost:3000/api/public/otel/v1/traces}
      # ⚠️ 必须带 /v1/traces：Spring Boot 的 OTLP 配置是【完整 URL，不会自动拼接路径】
      #    只写 /api/public/otel 会 404（curl 实测：带 /v1/traces 才 200）
      transport: http         # Langfuse 只支持 OTLP over HTTP（gRPC 不支持）
      headers:
        Authorization: "Basic <base64(public_key:secret_key)>"   # Langfuse 项目 API Key 的 Basic Auth
        x-langfuse-ingestion-version: "4"   # 实时摄入（不加最多延迟 10 分钟）
    metrics:
      export:
        enabled: false        # 只导 trace 不导 metrics（metrics 发到 Langfuse 会 404 刷屏）
spring:
  ai:
    chat:
      observations:
        log-prompt: true      # 把 Prompt 内容写进 span（默认 false = 隐私考虑）
        log-completion: true  # 把模型回复写进 span
```

**踩过的坑**：
- **Boot 3.5.11 的 OTLP 前缀是 `management.otlp.tracing`**（反编译 `OtlpTracingProperties` 坐实；Boot 3.4 是 `management.opentelemetry.tracing.export.otlp.*`，结构改过，别抄旧教程）；
- **endpoint 必须带 `/v1/traces`**：Spring Boot 把配置值原样传给 `OtlpHttpSpanExporter.setEndpoint`（完整 URL 语义），不追加路径；官方文档的短路径是给标准 OTel SDK 环境变量用的（SDK 会自动拼）；
- **`Authorization` 是 Langfuse 项目 `public_key:secret_key` 拼起来再 base64**（`printf "pk-lf-xxx:sk-lf-xxx" | base64`），与 compose 里 `LANGFUSE_INIT_PROJECT_*` 一一对应，改一边必须同步另一边；base64 只是编码不是加密，别提交公开仓库。

## 4. Langfuse v3 自托管（全坑实录）

### 4.1 v3 架构 vs v2（最大认知更新）

| | v2 | **v3** |
|---|---|---|
| 数据库 | 只要 Postgres | **Postgres（元数据）+ ClickHouse（traces 事件存储）** |
| 队列 | 无 | **Redis + MinIO(S3)**，事件经 S3 队列由 **worker** 消费写 ClickHouse |
| 应用容器 | 单容器 | **web（langfuse:3）+ worker（langfuse-worker:3 独立镜像）** |

**一句话**：v3 的事件流是 `web 收 OTLP → 写 S3 → worker 消费 → 写 ClickHouse`，**没有 worker，ClickHouse 永远是空的**（我们实际踩到：traces 一直 0 条）。

### 4.2 一键部署（docker/langfuse/langfuse-standalone.yml，6 服务）

```yaml
name: langfuse          # 显式 project 名 → 网络 langfuse_default，与 milvus/nacos 的网络彻底隔离
services:
  db:          postgres:16
  clickhouse:  clickhouse/clickhouse-server:24
  redis:       redis:7-alpine
  minio:       minio/minio:RELEASE.2024-05-28T17-19-04Z   # 复用本地已有镜像（milvus 同款）
  langfuse-web:      langfuse/langfuse:3        # 3000 端口
  langfuse-worker:   langfuse/langfuse-worker:3 # 独立镜像！langfuse:3 里没有 worker 包
```

### 4.3 环境变量硬性要求（逐一踩过）

| 变量 | 要求 | 踩坑实录 |
|---|---|---|
| `CLICKHOUSE_URL` / `CLICKHOUSE_MIGRATION_URL` | 必填 | 缺 → 启动报 `CLICKHOUSE_URL is not configured` |
| `CLICKHOUSE_CLUSTER_ENABLED` | **单节点必须 `false`** | 默认 true 会按集群模式执行命令报错 |
| `LANGFUSE_INIT_ORG_ID` | **3.2x+ 必填** | 不设 → 所有 `LANGFUSE_INIT_*` 被**静默忽略**（日志明确 warning） |
| `LANGFUSE_INIT_PROJECT_ID` | **必填** | 不设 → 项目不创建、API key 不生成（`Invalid credentials`） |
| `LANGFUSE_INIT_USER_EMAIL` | **必须合法邮箱** | `admin@localhost` → ZodError `Invalid input`，改 `admin@example.com` |
| `LANGFUSE_S3_EVENT_UPLOAD_*` | **3.2x 强制** | 不配 → ZodError `expected string, received undefined`；配了没 worker → 事件卡 S3 |
| `ENCRYPTION_KEY` | **`openssl rand -hex 32`（64 位 hex）** | 用 base64 格式 → 校验不过 |
| `NEXTAUTH_SECRET` / `SALT` | `openssl rand -base64 32` | — |

### 4.4 两个镜像级坑

- **minio 镜像没有 curl**：healthcheck 用 `curl -f http://localhost:9000/minio/health/live` 必挂（容器活着但永远 unhealthy，进而卡住依赖它的服务）。改 **bash 内置 /dev/tcp 探测**：
  ```yaml
  healthcheck:
    test: ["CMD", "bash", "-c", "</dev/tcp/127.0.0.1/9000"]
  ```
- **langfuse:3 镜像没有 worker 包**（`/app/packages/` 只有 shared）：worker 必须用独立镜像 `langfuse/langfuse-worker:3`；用 `langfuse:3 + command` 会 `MODULE_NOT_FOUND`，且 web+worker 同跑迁移会因抢 Postgres advisory lock 死锁。

### 4.5 网络隔离要点（多 compose 共存）

- compose **服务名 DNS 按网络隔离**：langfuse 的 `minio:9000` 只在 `langfuse_default` 解析，碰不到 milvus 的；
- 同目录多 compose 默认 project 名都是目录名 → 共用 `xxx_default` 网络（本项目 nacos 和 milvus 曾共网）；**给每个 compose 加顶层 `name: xxx` 显式隔离**；
- 容器内端口（minio 9000）各自网络命名空间独立；**只有显式 `ports` 映射才占宿主机端口**（milvus-minio 没映射宿主机，langfuse-minio 映射 9090，错开）。

## 5. Guardrails：没有现成模块，就用 Advisor 手写

### 5.1 为什么不用现成的

Maven Central **没有 `spring-ai-guardrails` 模块**（搜 0 结果），Spring AI 1.1.2 本地 jar 里也搜不到 Guardrails 类——1.1.x 没有护栏框架。但护栏本质就是"**调用前一道闸 + 返回后一道闸**"，而 Advisor 恰好提供这两个切点 → **手写是正解**。

### 5.2 Spring AI 1.1.2 的 Advisor API（新版，注意与旧教程差异）

```java
public class GuardrailAdvisor implements CallAdvisor, StreamAdvisor {
    // 非流式：完整请求/响应，可短路（不调 chain.nextCall 模型就不参与）
    ChatClientResponse adviseCall(ChatClientRequest request, CallAdvisorChain chain);
    // 流式：Flux<ChatClientResponse>，同样可短路
    Flux<ChatClientResponse> adviseStream(ChatClientRequest request, StreamAdvisorChain chain);
    int getOrder();   // 排序：-100 = 最先执行输入检查
    String getName();
}
```

- 用户输入从 `request.prompt().getInstructions()` 取（`List<Message>`，过滤 `MessageType.USER` 取最后一条 `getText()`）；
- 旧教程的 `RequestResponseAdvisor` 在 1.1.2 已换成 `CallAdvisor + StreamAdvisor`（`ChatClientRequest` 是 Record，`mutate()` 改请求）。

### 5.3 输入闸（拦截策略：短路而非抛异常）

```java
private String checkInput(ChatClientRequest request) {
    // 1) 超长  2) 敏感词（忽略大小写包含匹配）  3) 越狱特征（正则）
    ...
    return reason;   // null = 放行
}
// 命中 → 构造"提示语"假响应，模型不参与
private ChatClientResponse blockedResponse(ChatClientRequest request, String reason) {
    ChatResponse cr = ChatResponse.builder()
            .generations(List.of(new Generation(new AssistantMessage(text))))
            .build();
    return ChatClientResponse.builder().chatResponse(cr).context(request.context()).build();
}
```

**为什么短路而不是抛异常**：抛异常要 Controller 改代码、前端要处理错误流；短路 = 返回一条正常消息（"⚠️ 已拦截"），**Controller 零改动、前端体验一致、模型省一次调用**。

### 5.4 输出闸（PII 脱敏）

```java
ChatResponse newResponse = ChatResponse.builder()
        .from(chatResponse)                 // 复制原响应其余元数据
        .generations(List.of(new Generation(new AssistantMessage(masked))))
        .build();
```

正则（yml 配置）：手机号 `1[3-9]\d{9}` / 身份证 `\d{17}[\dXx]` / 邮箱 `[\w.+-]+@[\w-]+(\.[\w-]+)+`，命中替换为 `***`。

### 5.5 流式脱敏的深坑（重点）

**现象**：聊天页（SSE 流式）复述手机号 → 没脱敏；非流式正常。

**根因**（反编译 + 日志坐实）：**DeepSeek 流式块的 `textContent=null`**！真实流式块的 `DeepSeekAssistantMessage` 文本不在 `getText()`（content() 内部有聚合器从别处提取），导致：
- 逐块 `sanitize`：每块是增量 token（"1"、"3"、"8"），单块拼不出 11 位手机号 → 正则永远匹配不上；
- 手动 `collectList` 合并重建块：合并时 `getText()` 全为 null → 拼出一堆 "null" 字符串，且重建块会被 content() 内部聚合逻辑搞出 `data:null×N`。

**最终方案**：Advisor 流式只做输入拦截 + 透传；**流式脱敏挪到 `ChatService.stream`**——先 `collectList()` 收集完整 token → `String.join` 拼全文 → `guardrailAdvisor.maskPii(full)` → 单条发出（用户选定"缓冲后整体脱敏"，牺牲打字机效果换 100% 脱敏）：

```java
public Flux<String> stream(String message, String conversationId) {
    return chatClient.prompt().advisors(...).user(message).stream().content()
            .collectList()
            .flatMapMany(tokens -> Flux.just(guardrailAdvisor.maskPii(String.join("", tokens))));
}
```

**经验**：流式数据流里，**不要凭直觉假设"块 = 完整文本"**——不同模型适配器的流式块结构不同（DeepSeek 的 textContent 就是 null），先加日志打印块的真实结构再动手。

### 5.6 配置化（guardrail.*）

```yaml
guardrail:
  enabled: true
  max-input-chars: 2000
  sensitive-words: [偷税漏税, 制造炸弹, ...]
  jailbreak-patterns: ["忽略.*(之前|以上|所有).*(指令|规则|设定|限制)", ...]
  pii-enabled: true
  pii-patterns: ["1[3-9]\\d{9}", ...]
  blocked-reply: "⚠️ 该内容已被安全护栏拦截，未发送给模型。"
```

`GuardrailProperties` 用 `@Component + @ConfigurationProperties` 组合（Spring Boot 自动绑定，无需 `@EnableConfigurationProperties`）；正则懒编译缓存（`volatile` 双检锁）。

## 6. 工程化杂项修复合集（每个都值得记）

### 6.1 MySQL 时间非东八区（UTC 早 8 小时）

**根因**：MySQL 容器（bitnami 镜像，无 TZ 环境变量）会话时区是 UTC，`CURRENT_TIMESTAMP` 生成 UTC 时间。

**修复**（一行配置 + 关键认知）：
```yaml
spring:
  datasource:
    hikari:
      connection-init-sql: "SET time_zone = '+08:00'"
```
- **必须用数值偏移 `+08:00`**：MySQL 默认没加载 IANA 命名时区表，`SET time_zone='Asia/Shanghai'` 会报 "Unknown or incorrect time zone"（`forceConnectionTimeZoneToSession=true` 也是这个下场）；
- **TIMESTAMP 内部存 UTC 时刻、按会话时区显示** → 改会话时区后**历史 + 新数据全部自动正确**，无需 UPDATE；
- **验证要用应用接口**（`/api/obs/logs` 的 createdAt），`docker exec` 进容器是独立 UTC 会话会误导你。

### 6.2 SchemaMigration 删除，schema.sql 成唯一建表来源

之前有 `SchemaMigration`（CommandLineRunner 幂等 ALTER 补列兜底老库）。老库早已迁移完成、schema.sql 已完整覆盖全部表（conversation 含 type、rag_file 含 content_hash、task_ticket、ai_call_log）→ 删除该类，`spring.sql.init.mode=always` + `CREATE TABLE IF NOT EXISTS` 成为唯一真相源。**教训**：增量迁移脚本是"债"，库结构稳定后该清就清。

### 6.3 页面导航统一

6 个页面（index/rag/agent/multimodal/agent6/obs）nav 统一：brand `🤖 AI Workshop`、绝对路径、一致文字（聊天/知识库/Agent/多模态/Agent编排/可观测），obs 入口全站可见。

### 6.4 环境变量坑（Bash 跑服务必看）

本机 shell 有全局变量 `SERVER__PORT=0`（双下划线映射 `server.port`，优先级高于 yml）→ 用命令行 `mvn spring-boot:run` 时**端口全随机**！启动前必须 `env -u SERVER__PORT -u SERVER__HOST`。IDE 里跑不受影响。

## 7. Docker 部署（单阶段）

### 7.1 Dockerfile（单阶段：构建 + 运行一个镜像）

```dockerfile
FROM maven:3.9-eclipse-temurin-17
WORKDIR /app
# 1) 先拷 pom 单独下载依赖（Docker 层缓存：依赖不变时后续构建不重新下载）
COPY pom.xml .
COPY ai-workshop/pom.xml ai-workshop/pom.xml
COPY mcp-nacos-server/pom.xml mcp-nacos-server/pom.xml
RUN mvn -q dependency:go-offline -pl ai-workshop -am || true
# 2) 拷源码打包
COPY . .
RUN mvn -q package -pl ai-workshop -am -DskipTests
EXPOSE 9999
ENTRYPOINT ["java", "-jar", "/app/ai-workshop/target/ai-workshop-0.0.1-SNAPSHOT.jar"]
```

不分阶段（用户要求）：简单直接，代价是镜像带 Maven 体积大。

### 7.2 compose 一键起（docker/app-deploy.yml）

- 主应用容器化，**外部依赖（MySQL/Milvus/Ollama/Langfuse）复用宿主机**：容器里用 `host.docker.internal` 访问宿主机 localhost（`extra_hosts: host.docker.internal:host-gateway`）；
- **环境变量覆盖、yml 零改动**：`SPRING_DATASOURCE_URL` / `RAG_VECTORSTORE_MILVUS_HOST`（@Value 支持环境变量）/ `SPRING_AI_OLLAMA_BASE_URL` / `LANGFUSE_OTLP_ENDPOINT` / `MCP_NACOS_URL`；
- **容器版精简 MCP**：容器内无 stdio Python 环境 → `SPRING_AI_MCP_CLIENT_ENABLED=false`；配套把 `McpConfig` 注入改 `@Autowired(required = false)`（MCP 真正可选，注释原本意图）；
- API Key 走 `.env`（`docker/.env.example` 模板，compose 自动读取）。

## 10. 阶段收获

1. **观测是横切关注点**：Spring AI 用 Micrometer Observation 实现"加一个 Handler Bean，全链路自动可观测"，业务代码零侵入——这是框架设计的精髓；
2. **"没有现成模块"不是障碍**：Guardrails 用 Advisor 手写，反而把 Advisor 机制吃透（短路 vs 抛异常、order 排序、流式/非流式双入口）；
3. **流式不等于简单**：流式数据流的块结构因模型而异（DeepSeek textContent=null），动手前先打印真实结构；
4. **版本钉死的生态要警惕**：Boot 3.5.11 的 OTLP 前缀、Langfuse v3 的 INIT_* 要求、minio 无 curl——**以反编译/日志为准，不抄旧教程**；
5. **工程化的核心是"可回退 + 可解释"**：时区用会话级修复（历史数据自动正确）、Milvus 重置先备份、Docker 单阶段先跑通再优化。
