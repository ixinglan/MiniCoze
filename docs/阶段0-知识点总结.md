## 2. Maven BOM 依赖管理（版本不打架的关键）

阶段 0 用到 4 个 BOM，统一管版本，业务依赖**不用写 `<version>`**：

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.5.11</version>
</parent>

<dependencyManagement>
    <dependency> <!-- Spring AI 官方 BOM -->
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-bom</artifactId>
        <version>1.1.2</version>
        <type>pom</type><scope>import</scope>
    </dependency>
    <dependency> <!-- 阿里 BOM（agent 框架 / graph / document-reader 等） -->
        <groupId>com.alibaba.cloud.ai</groupId>
        <artifactId>spring-ai-alibaba-bom</artifactId>
        <version>1.1.2.2</version>
        <type>pom</type><scope>import</scope>
    </dependency>
</dependencyManagement>
```

**核心 starter（阶段 0）**：
- `spring-ai-starter-model-deepseek` —— DeepSeek 对话模型
- `spring-ai-starter-model-ollama` —— 本地 Ollama（embedding 用）
- `spring-boot-starter-web` —— REST 接口 + 内嵌 Tomcat

> 💡 BOM 的意义：Spring AI 迭代快、版本多，用 BOM 锁版本能避免"DeepSeek starter 和 spring-ai-core 版本不一致"这种玄学报错。

## 3. Spring AI 核心抽象：ChatModel 与 ChatClient

这是阶段 0 最该吃透的一对概念。

### 3.1 ChatModel（底层抽象）
所有聊天模型（DeepSeek / 通义千问 / OpenAI / Ollama…）都实现统一的 `ChatModel` 接口。
**屏蔽厂商差异**——换模型只改配置，业务代码不动。

### 3.2 ChatClient（高级对话入口）
`ChatClient` 是构建在 `ChatModel` 之上的 Fluent API，比直接用 `ChatModel` 更顺手：

```java
chatClient.prompt()          // 发起一次对话
        .user(message)       // 设置用户消息
        .system("你是一个…")  // 可临时覆盖系统提示词
        .call()              // 非流式：一次拿结果
        .content();          // 取出文本

chatClient.prompt()
        .user(message)
        .stream()            // 流式：逐 token
        .content();          // 返回 Flux<String>
```

为什么用 `ChatClient` 而不是直接 `ChatModel`：链式调用更清爽、加 system prompt 方便、后续阶段接 **Advisor**（记忆/日志/守卫）也是挂在 ChatClient 上。

### 3.3 Bean 注册与注入
DeepSeek starter 自动配置会把实现注册成名为 **`deepSeekChatModel`** 的 `ChatModel` Bean。
因为后面还引入了 Ollama（也可能提供 ChatModel），我们用 `@Qualifier` 精确指定：

```java
@Bean
public ChatClient chatClient(@Qualifier("deepSeekChatModel") ChatModel chatModel) {
    return ChatClient.builder(chatModel)
            .defaultSystem("你是一个友好、专业的 AI 助手，使用简体中文回答。")
            .build();
}
```

> 🔑 **记住 Bean 名 `deepSeekChatModel`** —— 以后出现 "expected single matching bean but found 2" 这类报错，基本就是 ChatModel 不唯一，用 `@Qualifier` 指定它就能解。

## 4. 供应商接入：DeepSeek（OpenAI 兼容协议）

DeepSeek 在 Spring AI 里是**官方原生支持**的，底层走 OpenAI 兼容协议，所以接入极简：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${AI_DEEPSEEK_API_KEY:}      # 走环境变量，不写死代码
      base-url: https://api.deepseek.com
      chat:
        options:
          model: deepseek-v4-flash          # 或 deepseek-v4-pro（更强/更贵）
```

- **模型名**：`deepseek-v4-flash`（便宜快）/ `deepseek-v4-pro`（强）
- **密钥安全**：用 `${ENV:默认值}` 占位符从环境变量读，配合 `.gitignore` 绝不进仓库
- V4 特性：原生多模态**输入**（能看图），但**不提供 embedding、不支持文生图输出**——这就是阶段 3/5 要补别家模型的原因

## 5. 双模型骨架（阶段 0 的进阶加分项）

> **一个应用 = DeepSeek（ChatModel，对话）+ Ollama（EmbeddingModel，向量化）**

| 模型 | 提供的接口 | 用途 |
|---|---|---|
| DeepSeek V4（云端） | `ChatModel` | 对话、流式、图片理解 |
| Ollama bge-m3（本地） | `EmbeddingModel` | 把文本转向量，阶段 3 RAG 用 |

```yaml
spring:
  ai:
    ollama:
      base-url: http://localhost:11434
      chat:
        enabled: false        # ⚠️ 关键：关掉 Ollama 的 ChatModel
      embedding:
        enabled: true
        options:
          model: bge-m3       # 中文 RAG 推荐
```

**⚠️ 这个坑必须记住**：Ollama starter 默认**也会注册一个 `ChatModel` Bean**，会和 DeepSeek 的 `ChatModel` 抢注入点，导致启动报"bean 不唯一"。所以在 `application.yml` 里把 `spring.ai.ollama.chat.enabled=false`，只留 embedding。

为什么选 Ollama 而不是再接一个云 embedding 服务：免费、本地跑、不用第二个 API key，还能顺带教你"多供应商混用"这个 Spring AI 的核心范式。

## 6. 流式输出：SSE（Server-Sent Events）

### 6.1 为什么需要流式
大模型回答是"边生成边吐字"的。非流式要等全部生成完才返回，用户干等；流式能做**打字机效果**，体验好很多。

### 6.2 后端：Flux → SseEmitter
`ChatClient.stream().content()` 返回响应式 `Flux<String>`。在 Spring MVC（Servlet 容器）下，用 `SseEmitter` 把 Flux 桥接到 HTTP 响应：

```java
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestParam String message) {
    SseEmitter emitter = new SseEmitter(0L);     // 0 = 不限超时
    chatService.stream(message).subscribe(
        token -> {                                // onNext：每个 token 推一次
            try { emitter.send(token); } catch (IOException e) { emitter.completeWithError(e); }
        },
        emitter::completeWithError,               // onError
        emitter::complete                         // onComplete：正常结束
    );
    return emitter;
}
```

- `TEXT_EVENT_STREAM_VALUE` = `text/event-stream`，告诉浏览器这是 SSE 流
- `SseEmitter(0L)` 表示不超时（长回答也不会被掐断）

### 6.3 前端：浏览器原生 EventSource
`EventSource` 是浏览器内置 API，专门消费 SSE，**只支持 GET**（这也是流式接口用 GET 的原因）：

```javascript
const es = new EventSource('/api/chat/stream?message=' + encodeURIComponent(text));
es.onmessage = (e) => { span.textContent += e.data; };  // 每收到一个 token 就追加
es.onerror   = () => es.close();
```

> SSE vs WebSocket：SSE 是**单向**（服务端→客户端）、基于 HTTP、自动重连，适合"模型推字"这种场景；WebSocket 是双向，适合聊天室/游戏。阶段 0 用 SSE 最简单。

## 7. 响应式编程基础（Project Reactor，浅尝即可）

阶段 0 只需懂一个概念就够：

- `Flux<T>`：0 到 N 个元素的**异步流**
- `.subscribe(onNext, onError, onComplete)`：三个回调分别处理"来数据了 / 出错了 / 结束了"

这里只是把 Flux "桥接"到 SseEmitter，**不用深入背压（backpressure）、操作符链**——后面做 Agent 编排时会再碰到响应式，到时候再深挖。

## 8. REST 接口设计

阶段 0 暴露了 3 个接口，对应 3 种用途：

| 方法 | 路径 | 作用 | 注意点 |
|---|---|---|---|
| GET | `/api/chat/stream?message=` | SSE 流式对话 | EventSource 只支持 GET，所以参数走 query |
| POST | `/api/chat` | 非流式对话 | JSON `{ "message": "..." }` → `{ "reply": "..." }` |
| GET | `/api/chat/embed?text=` | 验证 Ollama embedding | 带 try-catch，Ollama 没起也不 500 |

## 阶段 0 → 阶段 1 的衔接

阶段 0 的对话是"一次性"的：每次请求都是全新的上下文，模型**不记得上一句**。
下一阶段要做的是**多轮记忆（ChatMemory + Advisor）**：

- `ChatMemory`：按会话 ID 存历史消息
- `Advisor`：在请求前后自动注入/截取历史，业务代码几乎不改

把"记忆"加上后，你的助手才真正像个"助手"而不是"复读机"。
